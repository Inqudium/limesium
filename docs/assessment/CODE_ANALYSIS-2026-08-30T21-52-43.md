## 1. Executive summary

The codebase is in an unusually hardened state for its age: every risky mechanism (body tees, MDC
scopes, the reactive commit-deferral state machine, fail-open guards, meter registration) carries an
explicit concurrency/lifecycle contract in its KDoc, and the pinned findings of prior audits are
visibly fixed and tested. This analysis found **no Critical and no High defects**. The risks that remain
cluster around one theme: the **freshly committed default correlation-id generator**
(`CountingCorrelationIdGenerator`, commit `7c1365d`) landed with its own documentation contradicting it,
with a silent public-API removal (`RANDOM_UUID`), and with stale documentation in four places — the
code itself is sound, the change management around it is not. A second, older cluster is a **quiet
divergence from Spring's own path semantics** under non-root deployments (`server.servlet.context-path`
/ WebFlux base-path), where include/exclude matching can silently deactivate logging. Everything else is
consistency-level.

**Test verdict** (test code was in scope):

1. *Reliability as a safety net / testability:* high. The suite is deterministic by construction —
   injected time (`NanoTimeSource`) and ids everywhere, zero `Thread.sleep`/`now()`/unseeded randomness
   in test code (verified by grep), event-driven awaits (`AwaitingAppender` with a semaphore and a
   documented cross-thread MDC snapshot), hand-driven async lifecycles instead of real waiting. The
   mutation thought experiment holds at the risky spots: assertions check exact values, exact messages,
   exact meter counts; the two `isNotNull()` occurrences are supplementary assertions inside otherwise
   exact tests. Concurrency tests create real contention (16×2000 with a shared start latch) and route
   worker failures into the test verdict via latch counts.
2. *Usage & coverage (test pyramid):* healthy shape. Fast deterministic unit tests carry the load
   (mock-driven filter lifecycles), topped by a thin, targeted layer of real-container integration tests
   (embedded Tomcat/Netty, a real Brave bridge) that pin exactly the convention-dependent behavior unit
   tests cannot prove. The score-4/5 production spots are all covered, mostly by both layers; fuzz
   targets guard the three parser/boundary components and replay their corpora in every build.
3. *Most significant gaps & anomalies:*
   - The new `CountingCorrelationIdGeneratorTest` is thorough but places its rationale blocks where the
     test-evidence tooling cannot see them, and deviates from the documented rationale format (finding 5).
   - The context-path divergence (finding 3) has no test in either twin — the include/exclude tests all
     run at root context.
   - ~160 of 323 tests carry no rationale block (tolerated by convention for simple tests; the
     generated test-evidence page shows the gap honestly).

### 🟡 Medium

- [x] 1. [FILE:LINE — `./limesium-common/src/main/kotlin/eu/inqudium/limesium/common/CorrelationIdGenerator.kt:17`] {Medium} {Confidence: high} {maintainability}
      KDoc of `DEFAULT` contradicts its value
  - **Status: FIXED (2026-08-30)** — `DEFAULT` KDoc now describes the counting generator and its 21-char format; `<h2>` headings converted to Markdown.
  - Symptom → cause: the doc on the production default reads "a random type-4 UUID per request" while the value is `CountingCorrelationIdGenerator()` (random prefix + counter, base 36) — the comment was not updated when commit `7c1365d` swapped the implementation.
  - Triggering condition: always (documentation is wrong at the exact point hosts read before overriding the bean).
  - Impact: maintainability / wrong operator expectations — a host relying on UUID shape (length 36, dashes, version nibble) for downstream parsing or validation is misled by the API doc itself.
  - Fix strategy: reword the `DEFAULT` KDoc to describe the counting generator (or point to its class doc); align the `<h2>`-HTML headings with the repo's Markdown KDoc style while there.

- [x] 2. [FILE:LINE — `./limesium-servlet-logging/docs/GUIDE.md:234` (+3 more, see pattern S1)] {Medium} {Confidence: high} {robustness}
      Silent breaking change around the default id generator: public `RANDOM_UUID` removed, id format changed, four documentation spots stale
  - **Status: FIXED (2026-08-30)** — all four doc spots now describe the counting default; ADR-0004 records the decision, the `RANDOM_UUID` removal and the release-note obligation.
  - Symptom → cause: commit `7c1365d` deleted the public constant `CorrelationIdGenerator.RANDOM_UUID` (source-breaking for hosts that pin it), changed the externally visible id format on the echoed `X-Correlation-Id` header (36-char UUID → 21-char base-36), and left `RANDOM_UUID`/"UUID by default" documented in the servlet GUIDE (`:234`), the reactive GUIDE (`:436`) and both `endpoint-logging-reference.yml` files — unlike the ADR-0002/0003 breaking changes, this one has no ADR/release-note trail.
  - Triggering condition: always for documentation readers; on upgrade for hosts referencing `RANDOM_UUID` or parsing the echoed id.
  - Impact: broken host builds on upgrade; consumer-side format assumptions break silently; docs contradict behavior.
  - Fix strategy: correct the four documented spots, and record the format/API change wherever the ADR-0002/0003 breaking changes are collected for the next release notes (possibly as a short ADR addendum).

- [x] 3. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:124` (twin: `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/RequestLoggingWebFilter.kt:72`)] {Medium} {Confidence: medium} {robustness}
      Path activation diverges from router semantics under a non-root context path
  - **Status: FIXED (2026-08-30)** — activation now matches `pathWithinApplication` in all three filters (context/base path stripped, honoring the documented handler-mapping semantics); pinned by a context-path test per twin; KDocs, GUIDEs and reference YAMLs updated. Logged paths stay raw and keep the context path.
  - Symptom → cause: include/exclude matching parses the raw `request.requestURI` (servlet) resp. the full `request.path` (reactive), which INCLUDE `server.servlet.context-path` / the WebFlux base-path — while Spring's own `PathPattern` handler mapping, which the GUIDE cites as the semantic model, matches the path WITHIN the application. Under a non-root deployment, include patterns modeled after MVC routes (`/api/**`) match nothing.
  - Triggering condition: only edge case — deployments with a configured context/base path AND non-empty `include-path-patterns` (silently logs nothing) or `exclude-path-prefixes` (silently stops excluding, e.g. `/actuator/health` reappears in the log).
  - Impact: silent, total or partial loss of exchange logging (or unwanted noise) exactly where the operator configured otherwise; no error, no warning, no test covers a non-root context in either twin.
  - Fix strategy: decide and document the reference frame (either match `pathWithinApplication` to honor the "as handler mapping does" claim, or document context-path inclusiveness loudly in the GUIDE/reference yml) and pin the chosen behavior with a context-path test per twin.

### 🟢 Low

- [ ] 4. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:48`] {Low} {Confidence: high} {consistency}
      Arrival-line MDC diverges between the twins since ADR-0002
  - Symptom → cause: the servlet arrival line logs under the chain scope, whose trace keys are whatever the host's tracing bridge put in the MDC (`traceId` + local `spanId`); the reactive arrival line overlays the traceparent-derived pair (`traceId` + `parentSpanId`). The reactive emitter's KDoc claims the arrival line is "identical … INCLUDING the MDC". Before ADR-0002 the claim held; the servlet twin's switch away from bridge capture broke it for the arrival line only.
  - Triggering condition: only with `log-request-start=true` and a tracing bridge (servlet) or traceparent (reactive).
  - Impact: maintainability/consistency — encoders see `spanId` on servlet arrival lines but `parentSpanId` on reactive ones; the completion events are unaffected.
  - Fix strategy: either open the traceparent overlay around the servlet arrival line as well (twin parity), or correct the reactive KDoc claim and document the arrival-line difference in the twin-difference tables.
