## 1. Executive Summary

Der Code ist im stilistischen Sinn reif: ktlint läuft im Build und ist grün, alle Kommentare und Bezeichner sind englisch, es gibt keine Wildcard-Imports, keine `!!`, kein `lateinit` im Hauptcode, keine `TODO`/`FIXME`, keine auskommentierten Reste, und die Kommentare erklären durchgehend das Warum statt das Was. "Java in Kotlin" ist praktisch nicht vorhanden: Immutability-first (`val`, schreibgeschützte Collections), Expression-Bodies (59 im Hauptcode, kein einziger Block-Body mit bloßem `return`), `require`/`check` (35 Stellen), `when`, Extension-Funktionen, `object` für zustandslose Einheiten und `fun interface` für die injizierbaren Nähte sind die gelebte Norm. Die Testkonvention aus CONTRIBUTING (Backtick-Namen, AssertJ, Rationale-Block, Given/When/Then, keine Mocking-Bibliothek) wird von allen 371 Testmethoden eingehalten.

Die Befunde konzentrieren sich auf zwei Cluster. Erstens die **öffentliche Oberfläche als Bibliothek**: die Servlet-Tee-Klassen sind `public`, während ihre reaktiven Zwillinge `internal` sind, und die Companion-Konstanten der öffentlichen `fun interface`s (`HeaderValueMasker.DEFAULT` u. a.) sind ohne `@JvmStatic`/`@JvmField` aus Java nur über `Companion.getDEFAULT()` erreichbar - obwohl das Projekt mit `@JvmOverloads` an allen drei Filterkonstruktoren Java-Aufrufer ausdrücklich bedient. Zweitens **kleine Konsistenzbrüche gegen die eigene Hausnorm**: drei Logger-Deklarationen, die vom Muster `private val internalLog` im Companion abweichen, ein manuelles `throw IllegalArgumentException` in einem Projekt, das sonst überall `require` nutzt, sowie zwei handgepflegte 16- bzw. 17-Feld-`toString`-Repliken der Properties-Datenklassen. Dazu kommen ein `Pair`-Rückgabetyp für ein Domänentupel und eine Handvoll Low-Politur (Dateinamen, Member-Reihenfolge, Gedankenstriche in einer Datei, unbenutzte Catch-Parameter).

Systemisch sind zwei Muster: die 16-fach replizierte Fail-Open-Berichtsform (`reportQuietly { metrics.wiringFailure(); internalLog.… }`) und das in 24 Testklassen kopierte Logback-Fixture (plus 11 Kopien des `keyValues`-Helfers) - beides gleichförmig, also kein Lesbarkeitsproblem, aber ein Wartungsvervielfacher, den das seit heute existierende `limesium-common`-Test-Jar auflösen könnte.

**Dokumentierte Projektkonventionen (Stufe 2).** CONTRIBUTING: Kommentardichte und Namensgebung der Umgebung angleichen, Kommentare nennen Randbedingungen statt den Code nachzuerzählen; "eine normative Quelle je Vertragsaussage" (seit Architektur-Review 2026-09-05); Tests `*Test.kt`, Rationale-Block `What is tested / Success criteria / Why it matters` plus `Given/When/Then`-Stufenkommentare; Fuzz-Targets in JAVA (`*FuzzTest.java`, Scorecard-Detektor). **Stack.** Kotlin 2.4.10 (Trailing Commas, `buildMap`, `_` in Catch seit 2.2 verfügbar), Java 21 als Ziel (Records, Pattern Matching, Switch-Expressions, Text Blocks in den Java-Quellen verfügbar), `kotlin-spring` aktiv (manuelles `open` ist kein Thema), JSR-305 strict.

**De-facto-Hausstil (Stufe 3), aus der Mehrheit des Codes abgeleitet.**
- Konstruktor-Injektion überall; Beans in `@AutoConfiguration`-Klassen mit `@ConditionalOnMissingBean`; `ObjectProvider` für optionale Host-Beans.
- Logger: `private val internalLog = LoggerFactory.getLogger(X::class.java)` im `companion object` (5 von 8 Deklarationen), daneben `exchangeLog` für den konfigurierbaren Exchange-Logger.
- Fail-open: `reportQuietly { metrics.<stage>Failure(); internalLog.<level>(…) }` in jedem Catch; `failOpen(onInterrupted, onFailure) { }` für vollständig einschließende Guards.
- Validierung mit `require`/`check` und Lambdanachricht; Vorbedingungen im `init`.
- Konstanten `SCREAMING_SNAKE` im Companion; enums mit Verhalten (`BodyLogMode.logs`, `EndpointLogField.format`); `fun interface` mit Companion-Default für injizierbare Nähte.
- Mehrere zusammengehörige Top-Level-Deklarationen pro Datei (`Mdc.kt`, `ExchangeLine.kt`, `CapturingDecorators.kt`), Dateiname beschreibt den Inhalt.
- Expression-Bodies für Einzeiler; Block-Bodies nur mit echtem Ablauf.
- Bindestrich-ASCII (` - `) als Gedankenstrich in Kommentaren (alle Dateien außer einer).
- Tests: `class XTest`, Backtick-Namen `should …` (371/371), `@Nested inner class \`Thema\`` für Gruppen (16 Dateien), AssertJ (alle asserting Dateien), Logback `ListAppender`/`AwaitingAppender` als Beobachter, `AtomicLong`-Ticker.

**Analysiert vs. nicht analysiert.** Alle 28 Kotlin-Hauptdateien der drei Module und alle 7 Java-Benchmarks vollständig gelesen; die 3 Java-Fuzz-Targets vollständig; von den 53 Kotlin-Testdateien 7 vollständig oder in großen Teilen (`ServerContract`, `RequestLoggingFilterTest`, `RequestLoggingWebFilterTest`, `HeaderValueMaskerTest`, `AwaitingAppender`, `MdcAdapterSwap`, `Servers`, `EndpointAccessorRegistryGuard`, `UndertowTestServer`), der Rest per repo-weiter Zählung (Namensschema, Rationale-Block, AssertJ, `@Nested`, `lateinit`, FQN-Inline).
