## 1. Executive summary

The codebase is unusually well explained for its size. Most production comments record concurrency, fail-open, capture-boundary or twin-parity constraints; public declarations are almost completely covered by KDoc; no TODO/FIXME/HACK/XXX markers, generated-source comments or commented-out code candidates were found. The high raw comment density is therefore not, by itself, debt.

The audit nevertheless found **9 actionable issues: 2 Critical, 3 High, 3 Medium and 1 Low**. The two critical issues are direct contradictions: the servlet auto-configuration still says trace identity is captured from bridge MDC although ADR-0002 and the current code explicitly retired that mechanism; the reactive public configuration calls its namespace identical “key for key” to the servlet twin immediately before declaring the reactive-only `variant` key. Both can drive a maintainer or consumer to the wrong conclusion.

The highest knowledge-loss risks are elsewhere: the one-metrics-instance-per-registry constraint lives only on an internal class, the counting correlation-id width is explicitly guarded only by prose, and several comments conflate bytes observed by a response write path with bytes delivered to a client. These require preservation and better carriers, not deletion.

Recommended pilot: **`limesium-reactive-logging` only**. It contains representative public configuration, lifecycle, body-capture, metrics and twin-contract patterns; it has high recent churn but avoids starting in the servlet twin's more intricate multi-container lifecycle. Acute delivery pressure is **[MISSING – please supply]**, so this recommendation is conditional on the module not being in a release freeze.

## 2. Scope and methodology

The audit followed five complementary passes:

1. A lexical Kotlin/Java scan counted physical lines and comment lines while excluding quoted and triple-quoted string content; it located TODO-family markers, suspicious commented-out declarations, comment prefixes, long runs, exact repeated blocks and top-level declarations without adjacent KDoc.
2. Every included file received a 1–5 triage score. Score is a review-priority measure, not a quality grade: public contract/why comments, lifecycle/concurrency complexity, churn and known contradictions outweighed raw volume.
3. All score-5 files and the public boundaries of both published modules were inspected manually; score-4 files were sampled around their longest/risk-bearing comment blocks. Shared/twin declarations, contract tests and reference YAMLs were compared.
4. Git history and blame were used for age-gap and drift checks. This is a young repository: apparent “one-year” churn is six days of concentrated development, and extraction/renames make path counts conservative for moved common code.
5. Comment claims were checked against executable behavior, tests, ADRs and documentation tooling. RFC/Spring claims were checked against [RFC 9110 §9.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.1), [Spring `ReactiveHttpOutputMessage`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/http/ReactiveHttpOutputMessage.html) and [Spring `AbstractListenerWriteProcessor`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/http/server/reactive/AbstractListenerWriteProcessor.html).

Conventions were taken from `./CONTRIBUTING.md`, ADR-0001 through ADR-0004, module API/reference documentation and the test-evidence generator. The controlling rule is that comments state constraints code cannot express rather than narrate code. Test comments are an explicit exception with a documented three-part rationale followed by Given/When/Then; they were not flagged merely for repetition. No repository convention defines `Rationale:`/`Invariant:`-style prefixes, so their absence is reported as a systemic observation, not treated as a broad violation.

## 6. Systemic patterns

1. **High density is mostly justified knowledge.** The densest areas explain concurrency publication, fail-open behavior, container lifecycle, reset semantics, trace identity and why two twins cannot share an implementation. A line-count reduction target would destroy useful controls.
2. **The public boundary is strong but not perfectly aligned.** Nearly every intended public declaration has KDoc and Dokka warnings are gated. The serious gaps are not missing prose; they are contradictory wording (CA-01/02), a hidden internal-only limit (CA-03) and one likely accidental public helper (CA-09).
3. **Twin duplication is a deliberate architecture choice.** Exact duplicated KDocs often describe intentionally identical contracts, and cross-module tests guard them. Prefer local twin comments plus executable parity tests over a remote “see other module” reference. Consolidate only genuinely dependency-free rules, as ADR-0003 already does.
4. **Review provenance has outlived its reports.** Six days of intensive audit/fix work produced many numbered proof suffixes. The code frequently retains the important failure mode, but anonymous report numbering is already degrading and has introduced formatting damage (CA-07).
5. **Test comments are a production documentation carrier.** The repetitive three-question + Given/When/Then form is intentional and generator-consumed. It should be validated, not minimized. CA-06 is a tooling integrity issue, not a request to remove test comments.
6. **Observation-boundary vocabulary needs one definition.** “Flowed,” “written,” “committed,” “delivered” and “received” are used too interchangeably across the twins. The code actually has careful stack-specific boundaries; a shared vocabulary would make those comments more precise without forcing false parity.
7. **Why-comments are not searchable by intent.** There are no agreed `Rationale:`/`Invariant:`/`Compatibility:`-style prefixes. This is not currently a convention violation, but it makes future audits depend on prose heuristics and encourages all-caps emphasis as an informal substitute.
8. **History signals are immature.** With only six days and 115 commits, “high churn” means concentrated construction/audit activity, not proven long-term instability. Re-run after normal maintenance history exists before deleting comments on an age/churn theory.

## 7. Implementation order and guardrails

### Five-pass remediation order

1. **Mechanical hygiene.** Repair only the seven proven line-splice artifacts (`review        // finding`, malformed possessive). Do not delete substantive comments or normalize case/voice in this pass.
2. **Sharpen public/internal KDoc.** Correct CA-01, CA-02, CA-05 and CA-08; if CA-09 must remain public, document it. Each edit must name the real observation/contract boundary, not merely shorten prose.
3. **Anchor provenance.** Resolve CA-07 against existing ADRs, named tests and performance reports. Delete only dead numeric suffixes after preserving the local decision and failure mode. Update links before pruning copies.
4. **Upgrade carriers.** Decide/enforce metrics ownership (CA-03), encode/test the correlation-id boundary policy (CA-04), make test-evidence extraction strict (CA-06), and narrow accidental API visibility (CA-09). This is the only pass that should alter production/test/tool behavior.
5. **Minimize only after preservation.** Remove wording that has become redundant because a current ADR, test, type or validation now carries it. Re-run the inventory and compare knowledge coverage, not just comment-line count.

### Safest top-three slices

1. **Trace-order truth slice (CA-01):** update one KDoc against existing ADR-0002 and the existing real-container trace tests. No production behavior change; review the remaining early-order rationale separately.
2. **Reactive configuration-contract slice (CA-02):** change the four public “identical” claims to “shared subset plus `variant`,” and assert the wording/shape through the already canonical reference test. No property or default changes.
3. **Metrics-ownership slice (CA-03):** add a same-registry/two-filter characterization test, choose shared-owner versus explicit unsupported wiring, then publish the decision on all three public filter entry points. Do not merely copy the internal warning without deciding the supported API.

CA-04 and CA-05 should follow immediately: the former needs a design decision and executable boundary; the latter is a contained terminology correction but touches an operator-facing observability contract.

### Guardrails

- Never use total comment lines or density as a deletion KPI. Use unresolved contradictions, missing carriers and dead references.
- For every changed/deleted comment, reviewers must answer: what information class was present; where is the residual information now; can that carrier drift; what test/link detects it?
- Adopt a small optional prefix vocabulary for new/high-risk why-comments: `Rationale:`, `Invariant:`, `Compatibility:`, `Safety:`, `Performance:`, `Workaround:`, `Assumption:`. Do not mechanically prefix every comment and do not rewrite stable prose solely for style.
- Keep test `What is tested` / `Success criteria` / `Why it matters` labels distinct from the production prefix vocabulary. Make the generator validate all three and report the exact file/method on failure.
- Keep Dokka `failOnWarning=true`; add no blanket suppression to make a cleanup pass green. Public declarations intentionally excluded from the supported API should be narrowed, not documented as accidental API by default.
- Preserve local concurrency/lifecycle comments at the mutation site even when an ADR exists. ADR = decision/history; local comment = immediate failure mode; test = executable invariant.
- For twin edits, update both modules or explicitly record the asymmetry, and run both contract suites/reference checks.
- For observability wording, use stack-accurate layers: application consumed request bytes; response bytes crossed the tee/write path; response committed; remote client receipt is generally unknown.
- Re-audit the pilot after 30 days or 10 merged behavioral PRs, whichever comes first. Compare recurrence of dead references, incomplete test rationale and contract contradictions—not raw prose volume.
