## 1. Executive summary

The module is structurally disciplined: exchange completion is guarded exactly once, mutable cross-callback state is volatile or atomic, time and correlation generation are injectable, DataBuffers are forwarded without ownership changes, and the high-risk error/commit paths have focused tests. No Critical or High defect was identified. The most important new defect is a cancellation race: the capture is read and logged immediately from `doFinally(CANCEL)`, although Reactive Streams permits already-requested `onNext` signals after cancellation and Reactor's mapped tee can still execute for them; the unsynchronized `ByteArrayOutputStream` can therefore be read while it is changing. A second cluster concerns the supposedly fail-open observability dependencies: incompatible host meters can abort application startup or suppress an exchange event, while the catch handlers themselves call counters and loggers without a secondary no-throw boundary. Two deterministic correctness edges remain in duration classification and trace parsing: positive sub-millisecond slow thresholds collapse to zero milliseconds, and malformed trace/span identifiers are accepted as W3C trace context. The auto-configuration also emits an inapplicable Reactor-propagation warning when the coroutine variant or a host filter owns the filter slot. Most effects corrupt or suppress observability rather than business responses, which keeps them below High, but the meter-registration path can prevent application startup and the recursive fail-open gap can disturb request assembly or response commit under its trigger.

**Test verdict.** The suite is a generally strong and mostly deterministic safety net: 74 focused tests cover normal, error, cancellation, commit-deferral, coroutine-MDC, body, metric, and auto-configuration paths, and one class uses a real Netty server. Its pyramid remains healthy, but the real-runtime layer always selects the coroutine filter because both optional coroutine libraries are present on the test classpath; the reference Reactor filter is therefore proven only with mock exchanges. The most consequential boundary tests are also synchronous and cannot expose the post-cancel body race, sub-millisecond threshold rounding, or malformed trace IDs. Local HTTP requests have no connect or response deadline, so a liveness regression can hang the suite instead of failing it promptly.

Most significant gaps and anomalies:

- no adversarial cancellation test emits an already-requested body buffer concurrently after `cancel`;
- no valid non-whole-millisecond slow threshold is tested;
- no malformed/non-hex/all-zero-parent `traceparent` case is tested;
- the real-Netty suite exercises `CoRequestLoggingWebFilter`, not the reference `RequestLoggingWebFilter`;
- real HTTP calls have no bounded timeout;
- the current `MdcScope` partial-install rollback is not covered by the existing test artifacts.

### 🟡 Medium

- [x] 1. [FILE:LINE — ./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/BoundedBodyCapture.kt:29] {Medium} {Confidence: high} {concurrency/reactive} Cancellation can make body capture mutate concurrently with its final log snapshot
  - Symptom → cause: a cancelled exchange can emit a body log and size sample while `tee` is still appending/counting a late, already-requested DataBuffer. `doFinally(CANCEL)` runs immediately after cancellation is forwarded, Reactive Streams still permits pending `onNext`, and Reactor 3.8.5's `FluxMap.cancel()` does not mark the mapper done; `ByteArrayOutputStream`, `totalBytes +=`, and `loggedValue` have no mutual exclusion or immutable terminal snapshot. The volatile total publishes preceding writes but does not prevent a later/concurrent mutation.
  - Triggering condition: a client cancellation races an asynchronous request or response body publisher that delivers an already-requested `onNext` after `cancel`; most likely under streaming/load or with a custom publisher.
  - Impact: corrupted/truncated body text, request/response size samples that disagree with the logged body, or a caught emission exception that drops the event. The HTTP exchange is already cancelled, but its observability result is nondeterministic.
  - Fix strategy: introduce an atomic freeze/snapshot operation used by terminal emission and make post-freeze capture a no-op, or synchronize capture mutation and snapshot creation without blocking the reactive chain for unbounded work. Add a deterministic publisher that holds an `onNext` across cancellation to prove the hand-off.

- [x] 2. [FILE:LINE — ./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/EndpointLoggingMetrics.kt:30] {Medium} {Confidence: high} {robustness} Host meter identity/type conflicts can abort startup or suppress the exchange event
  - Symptom → cause: all fixed meters are registered while the filter bean is constructed, outside any fail-open boundary. Micrometer throws when the same meter ID already exists with an incompatible type, so a shared host registry collision prevents the application context from starting. The body summaries are registered lazily at lines 126-132; a runtime collision there throws before `event.log()`, so enabling body-size measurement can drop the complete exchange event. A pre-existing compatible gauge is also silently reused while the filter mutates its own unregistered `AtomicLong`, disconnecting the visible gauge from actual exchanges.
  - Triggering condition: the host or another library pre-registers an `endpoint.logging.*` or `endpoint.*.body.size` meter with the same ID but a different type, or pre-registers the open-exchange gauge with different state.
  - Impact: application startup failure, silently incorrect open-exchange telemetry, or lost structured exchange events once the conflicting body metric is first recorded.
  - Fix strategy: treat metric setup and dynamic body-size recording as independently fail-open capabilities. Detect/reuse only compatible owned meters, degrade conflicting meters to no-op reporting without suppressing the log event, and make gauge state registry-scoped rather than instance-local.

- [x] 3. [FILE:LINE — ./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLogEmitter.kt:65] {Medium} {Confidence: high (gap) / low (trigger)} {robustness} The fail-open catch handlers invoke the same fallible diagnostics without a secondary guard
  - Symptom → cause: after catching a logger, MDC, callback, or wiring exception, the handlers immediately increment a Micrometer counter and write to an internal logger. If either reporting operation throws, that second exception escapes the catch. This is request-affecting before the chain (`wireOrNull`, request-start logging, commit-callback registration) and can disturb response commit inside the commit callback, contradicting the module's central no-request-impact contract.
  - Triggering condition: a global throwing logging filter/appender, a custom Counter implementation that throws on `increment`, or a registry/backend failure that affects the diagnostic path as well as the exchange logger. The suite already demonstrates that Logback level checks can throw, but its injected TurboFilter deliberately excludes the internal logger.
  - Impact: request assembly failure, response-commit failure, replacement/masking of the original observability exception, and incomplete fail-open metrics.
  - Fix strategy: make every diagnostic path explicitly no-throw, with independent containment around counter and internal-log reporting and no recursive dependency on the component that just failed. Preserve the original exception and restore interrupts/MDC before attempting optional diagnostics.

- [x] 4. [FILE:LINE — ./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLogEmitter.kt:111] {Medium} {Confidence: high} {correctness} Positive non-whole-millisecond slow thresholds are rounded down and misclassify exchanges
  - Symptom → cause: elapsed nanoseconds are first truncated to whole milliseconds, and `slowRequestThreshold.toMillis()` is independently truncated. A valid threshold of 500 microseconds becomes zero, so even a zero-millisecond exchange is always marked slow and escalated to WARN; a 1.5 ms threshold becomes 1 ms and flags exchanges that are still below the configured threshold. Extremely large valid Durations can also make `toMillis()` throw and drop the event through the emission guard.
  - Triggering condition: any configured positive threshold with sub-millisecond precision or, for overflow, an exceptionally large Duration.
  - Impact: wrong `endpoint_slow` values, systematically inflated WARN logs/alerts, and potentially a lost event for overflowing thresholds.
  - Fix strategy: compare elapsed monotonic time against the threshold at nanosecond precision with overflow-safe conversion, and round only the separately emitted duration field. Alternatively, reject unsupported precision and range during configuration binding with an explicit diagnostic.

- [x] 5. [FILE:LINE — ./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/Traceparent.kt:20] {Medium} {Confidence: high} {correctness/robustness} Invalid W3C trace and parent identifiers are accepted into MDC correlation fields
  - Symptom → cause: parsing checks only component counts/lengths and an all-zero trace ID. It accepts non-hex or uppercase IDs and an all-zero parent ID, although W3C requires lowercase hexadecimal identifiers and declares both all-zero IDs invalid. Those caller-controlled strings are then emitted under conventional `traceId`/`spanId` MDC keys as if they were valid tracing identities.
  - Triggering condition: a malformed or non-conformant incoming `traceparent`, for example a correctly sized non-hex trace ID or `0000000000000000` as parent ID.
  - Impact: false log-to-trace joins, invalid correlation fields, and incident searches that attribute an exchange to a span identity no conforming tracer accepts.
  - Fix strategy: validate lowercase hexadecimal shape and non-zero trace and parent IDs before returning either value. Keep any deliberate version/flags leniency explicit and coordinated with the sibling parser, but do not let it weaken identifier validity.

## 6. Systemic patterns

1. **Fail-open handling still trusts fallible reporting dependencies (approximately 11 catch branches).** Counting basis: manual enumeration of `catch` branches in `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt` and `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLogEmitter.kt`. Each branch performs a counter increment and/or internal logging after the original failure without a final no-throw boundary; finding 3 is the representative request-affecting effect. Metric construction/recording in finding 2 is the same trust assumption before and during emission.
2. **High-risk boundary tests use cooperative, whole-unit inputs rather than adversarial boundaries (at least 5 surfaces).** Counting basis: mutation thought experiments over cancellation/body, duration, trace parsing, real-runtime variant selection, and HTTP liveness. Cancellation uses `Mono.never()` with no in-flight body, thresholds use whole milliseconds, trace tests use only a valid header, the only real server selects the coroutine variant, and HTTP calls are unbounded. Findings 1 and 4-7 capture the concrete risks; this pattern explains why substantial line/path coverage does not close those boundaries.

| 1 — cancellation races the capture snapshot | **Fixed.** `BoundedBodyCapture` serializes every mutation and read under one uncontended `ReentrantLock` and gains `freeze()`; the emitter freezes both captures as its first step, so a late `onNext` is a no-op and body text and size sample are one snapshot.
