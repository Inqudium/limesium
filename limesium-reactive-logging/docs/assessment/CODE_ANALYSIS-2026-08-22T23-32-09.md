## 1. Executive summary

The module has a disciplined reactive core: both filter variants share one lifecycle, terminal completion is atomic, body capture is bounded and frozen, cancellation is preserved, time is injected, and fault handling is generally explicit. No Critical or High defect was identified, and every remediation claimed by the existing assessment history was checked against the current code before being treated as resolved. The most material remaining risk is the deferred-error completion point: Reactor executes `doFinally` after propagating the error downstream, so response commit may already be running or retrying when `onTerminal` tries to append a `beforeCommit` callback. Spring reports `COMMITTING` as committed and skips all commit actions when retrying from `COMMIT_ACTION_FAILED`; those semantics can produce an early event with incomplete final response data or strand an exchange in `AWAITING_COMMIT`. The coroutine variant has a separate fail-open gap because ambient MDC capture and `MDCContext` installation are logging-owned operations that can escape or be rethrown as handler failures. Runtime counter failures can also suppress otherwise viable exchange logging or make the reconciliation metrics claim that an already emitted event was dropped. The test suite is strong overall, but several Reactor auto-configuration contexts still leave module accessors in the JVM-global `ContextRegistry`, despite the targeted cleanup helper introduced for earlier findings. The globally rendered error-body omission was reverified but is not counted again: current code, README, integration test, and historical decision material consistently define it as an explicitly accepted WebFilter boundary.

**Test verdict:** The suite is a credible safety net with deterministic unit tests, context-runner coverage, and separate real-Netty integration classes for the Reactor and coroutine variants. Its pyramid is healthy, but the final-commit proof uses synchronous commit actions and therefore does not exercise a commit already in progress, an asynchronous commit action, or a successful retry after `COMMIT_ACTION_FAILED`. The most significant gaps and anomalies are:

- no controlled race between the error terminal callback and an already `COMMITTING` response;
- no retry case proving that an exchange does not remain in `AWAITING_COMMIT` after commit-action failure;
- no coroutine test with a failing MDC adapter during ambient snapshot or `MDCContext` installation;
- no selective counter-failure test where logging otherwise remains healthy;
- incomplete cleanup of JVM-global context accessors outside the two guarded test sites.

Spring Framework 7.0.8's local `AbstractServerHttpResponse` source was used to verify that `isCommitted` is true during `COMMITTING`, status and headers remain mutable until commit actions finish, commit actions are iterated from a `CopyOnWriteArrayList`, and a retry from `COMMIT_ACTION_FAILED` skips commit actions. Existing reports were read-only history and were consulted only after the current paths were reconstructed; the prior response-body boundary was checked against current source, README, and real-Netty test before being accepted as intentional.

The module performs no persistence, transactions, messaging, blocking remote/file I/O, custom scheduling, or virtual-thread work. Its short `ReentrantLock` sections protect only bounded in-memory body capture; Reactor signals and coroutine resumptions provide the principal concurrency surface. No Maven goal, test, application, or reproducer was executed because the governing prompt requires explicit go-ahead before local execution. - [ ] 1. [FILE:LINE — `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:185`] {Medium} {Confidence: high} {correctness / concurrency / reactive} Deferred error completion can run before final commit actions or be skipped by a commit retry
  - Symptom → cause: `doFinally` calls `actual.onError` before `onTerminal`, so the outer error renderer can already have moved the response to `COMMITTING`. Spring treats that state as committed although status and headers remain mutable until commit actions finish; lines 185 and 195 can therefore call `complete` while an asynchronous action is still changing selected data. There is also a lost-registration path: if the response is in `COMMIT_ACTION_FAILED`, `isCommitted` is false and the module appends its callback, but Spring's retry transition deliberately skips every commit action, so a successful retry can leave the exchange in `AWAITING_COMMIT` forever.
  - Triggering condition: An unhandled error whose response commit begins before terminal bookkeeping, especially with an asynchronous `beforeCommit` action; or an initial commit-action failure followed by a later successful response commit. The synchronous commit actions in current unit and Netty tests do not create either interleaving.
  - Impact: The event can carry a pre-final status/header set, classify the wrong outcome/level, or be lost while `endpoint.logging.exchanges.open` remains permanently elevated even though the response eventually committed.
  - Fix strategy: Do not treat `isCommitted=true` as equivalent to commit completion and do not rely on an action appended after `COMMIT_ACTION_FAILED`. Anchor deferred emission to a lifecycle signal that observes successful commit completion, with an explicit fallback for failed/abandoned commits, while retaining the atomic exactly-once transition.

At least **2 test classes** are affected, representing approximately **8 unguarded Reactor context starts** by manual condition/call-site review: `RequestLoggingAutoConfigurationTest` creates several Reactor contexts but guards only one method, and `RequestLoggingWebFilterReactorIntegrationTest` starts a real Reactor application without restoring the registry. `MdcContextPropagationTest` itself is correctly guarded, but its snapshot deliberately preserves pre-existing entries and therefore cannot repair accessors leaked by an earlier class. Remediation should be class-/suite-lifecycle based rather than attached only to the tests that explicitly assert registry content.

## 7. Remediation status (2026-08-22)

All five findings were re-verified against the code before remediation — finding 1 additionally against the local Spring Framework 7.0.8 `AbstractServerHttpResponse` source (`isCommitted` is `state != NEW && state != COMMIT_ACTION_FAILED`; the `COMMIT_ACTION_FAILED → COMMITTING` transition skips the action list), finding 5 against the Kotlin standard library. The module suite is green after the changes (`mvn -pl limesium-reactive-logging verify`: 114 tests, ktlint clean).

| Finding | Resolution |
|---|---|
| 1 — deferred completion before final commit actions / skipped by a commit retry | **Accepted boundary, documented — not fixed.** Both interleavings are real but unobservable from a `WebFilter`: `ServerHttpResponse` exposes `beforeCommit` only, never a commit-*completion* signal, and the commit state is private. (a) Terminal signal while the response is `COMMITTING` with an asynchronous action still in flight: the module completes immediately; the status it reads is already final (the renderer sets it before it commits), a header that action adds afterwards is missed. (b) `COMMIT_ACTION_FAILED` followed by a successful retry: the retry skips every action including the module's, so the exchange stays on the open-exchanges gauge although the client received the rendered status — the documented never-commits semantics, with the gauge as liveness signal. A `beforeCommit` registered during `COMMITTING` does not help either: Spring iterates a `CopyOnWriteArrayList` snapshot taken at subscription. Observing commit completion needs the `HttpHandler`/`WebHandler` integration point, which section 7.1 of CODE_ANALYSIS-2026-08-22T20-06-45.md already rejected as an architectural change. The KDoc of `ExchangeLifecycle.registerCommitCallback` and the race comment in `onTerminal` now state both residuals precisely. |
| 2 — coroutine MDC snapshot outside the fail-open boundary | **Fixed** for the snapshot. `CoRequestLoggingWebFilter.handlerMdcOrNull` guards `MDC.getCopyOfContextMap()`: on failure the chain runs WITHOUT the handler `MDCContext`, the degradation is counted `stage=wiring` and warned on the module logger, and the exchange lifecycle continues (event emitted, gauge closed). Pinned in `CoRequestLoggingWebFilterTest` with an injected adapter whose snapshot throws (the `MDC.setMDCAdapter` swap is now the shared `installMdcAdapter` helper, also used by `MdcScopeTest`). Residual, documented in the class KDoc: an adapter that throws INSIDE `MDCContext`'s install/restore surfaces from `withContext` indistinguishably from a handler failure and is treated as one — such an adapter breaks every `MDCContext` user in the host, so no parallel mechanism was built. |
| 3 — operational counter increments not isolated | **Fixed.** `EndpointLoggingMetrics.correlationId` and `eventEmitted` run through `updateQuietly`: a throwing host counter is counted `stage=wiring` and warned, the exchange is wired and logged regardless, and a successful `.log()` is never reported as an emission failure. `RequestLoggingWebFilterMetricsTest` pins both with a registry that throws selectively on one meter while everything else is healthy (event emitted, `emission=0`, `wiring=1`). Body-size summaries were already isolated in the emitter; the gauge is an `AtomicLong` and cannot throw. |
| 4 — accessors leak from Reactor contexts into the JVM-global registry | **Fixed.** `RequestLoggingAutoConfigurationTest` snapshots/restores the registry in `@BeforeEach`/`@AfterEach` around EVERY method (the per-method guard of the accessor assertion is folded into it); `RequestLoggingWebFilterReactorIntegrationTest` does the same in static `@BeforeAll`/`@AfterAll`, which bracket the Spring context load (the context is created when the first test instance is prepared, after `@BeforeAll`). |
| 5 — conformance-fixture reader never closes its stream | **Rejected — false positive.** Kotlin's `Reader.readLines()` is implemented as `forEachLine`, which is `useLines`, which is `buffered().use { ... }`: the `BufferedReader` — and with it the underlying classpath `InputStream` — is closed when `readLines()` returns. No change. |
