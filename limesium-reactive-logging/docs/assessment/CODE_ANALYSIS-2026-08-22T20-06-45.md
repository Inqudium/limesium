## 1. Executive summary

The module has a disciplined and substantially remediated core: exchange completion has one atomic state transition, body snapshots are frozen under a lock, downstream Reactor assembly is deferred, coroutine cancellation is rethrown, callback failures are contained, and both filter variants have real-Netty coverage. No Critical or High defect was identified. The most important remaining correctness defect is on the feature's hardest path, deferred error emission: the callback is named and tested as if it observed the final commit, but Spring executes `beforeCommit` actions in registration order and this early filter registers its action before downstream and error-rendering actions. It can therefore emit a stale status and incomplete response headers, or emit an event for a commit that a later action aborts.

Trace correlation has a second material semantic defect. The incoming `traceparent` parent ID is the caller's span, yet the module publishes it under the conventional local `spanId` MDC key; it also deliberately accepts invalid version/flags fields. This creates false log-to-span joins on every valid propagated trace and accepts joins that a conforming tracer must reject. Header masking is likewise weaker than its security-facing name and documentation imply: the length plus 32-bit `String.hashCode()` fingerprint is collision-prone and supports cheap dictionary confirmation of low-entropy secrets. Two further Medium findings are explicit residual boundaries rather than hidden surprises: globally rendered error bodies bypass both response logging and response-size measurement, and a non-blank but syntactically invalid correlation-header name is accepted at startup and can degrade every request into unlogged pass-through.

The lower tier contains a documented request re-subscription overcount, byte-boundary corruption of truncated multi-byte text, loss of Spring's optimized single-buffer response path, and test leakage of JVM-global context accessors. None changes application data or blocks a request under the normal framework implementations; the impact is incorrect or incomplete observability, avoidable hot-path overhead, and localized test-order risk.

**Test verdict.** The 18-file suite is broad, mostly deterministic, and has a healthy unit/context/real-Netty pyramid. Its main weakness is not missing volume but assertions that canonize or avoid the remaining boundaries: the deferred-error tests set status before commit without a later mutating action, the trace test explicitly requires invalid headers to parse, the masking pin freezes the weak hash format, the error integration test requires the body omission, and truncation uses ASCII only. No fresh build or reproducer was run because the governing prompt requires explicit go-ahead before execution.

[FILE:LINE — `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:100`] {Medium} {Confidence: high} {correctness / concurrency} Deferred error emission runs during an early `beforeCommit` action, not after the final status and headers are known
  - Symptom → cause: the filter registers its commit action before invoking the downstream chain. On an uncommitted error, `onTerminal` moves the exchange to `AWAITING_COMMIT`; when commit begins, that early action stores the current status and immediately calls `complete`. Spring Framework 7.0.8 stores actions in registration order and concatenates them before applying the response. A downstream/error-handler action registered later can still change status or headers, or fail the commit, after the module has irreversibly logged and closed its gauge. `isCommitted` also returns true during `COMMITTING`, so the terminal-side fallback has the same premature-finality risk in its race branch.
  - Triggering condition: an unhandled error takes the deferred path and a later `beforeCommit` action mutates status/selected headers or aborts commit. Security/session/header filters commonly use later commit actions; a status mutation is less common but legal.
  - Impact: the event can carry a status the client did not receive, omit final response headers, classify the wrong outcome/level, and count an exchange as emitted even when the commit subsequently fails. This violates the module's central claim that deferred emission observes the rendered final response.
  - Fix strategy: redesign the deferred path around an observation point that runs after all commit actions and final response application, while preserving exactly-once completion and a fallback for never-committing errors. If the WebFilter boundary cannot observe that point, narrow the published contract and expose the pre-commit limitation explicitly. A deterministic test should register a later action that changes 500 to 503 and adds a selected header, then assert what reaches both the response and event; a second action should fail commit.

[FILE:LINE — `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/Traceparent.kt:26`] {Medium} {Confidence: high} {correctness / robustness} Caller propagation data is published as the local trace/span identity, and the parser deliberately accepts invalid W3C fields
  - Symptom → cause: `Traceparent.parse` returns `(trace-id, parent-id)`, `ExchangeLifecycle` assigns the second value to `spanId`, and `MdcScope` emits it under the conventional `spanId` MDC key. W3C defines `parent-id` as the caller's request/span ID, not the server span created for this exchange. The parser also accepts version `ff`, non-hex/wrong-length flags, and extra fields because it validates neither version nor flags and only requires at least four parts; `TraceparentTest` explicitly requires `ff-...-zz` to parse. A valid-looking inbound header is trusted even if no tracer participates or the host rejects/restarts that context.
  - Triggering condition: the span mismatch occurs for every accepted incoming `traceparent`; invalid-join behavior occurs for malformed headers such as version `ff` or flags `zz`, or when host tracing intentionally does not adopt the inbound context.
  - Impact: `traceId` may describe an untrusted inbound context rather than the active server trace, while `spanId` deterministically points to the caller span. Log-to-current-span links therefore fail or attach the server event to the wrong service; malformed context can create links that conforming tracing infrastructure does not contain.
  - Fix strategy: obtain the active server observation/tracing identity at an execution point where it exists, or publish inbound values under explicitly parent-oriented names rather than conventional local trace/span keys. Make parsing W3C-conformant for version 00 and handle future versions per the specification; replace the test that pins invalid acceptance with rejection and active-span integration cases.

[FILE:LINE — `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/RequestLoggingProperties.kt:180`] {Medium} {Confidence: high} {correctness / data exposure} Header “masking” uses a 32-bit non-cryptographic hash that neither protects low-entropy secrets nor supplies a reliable fingerprint
  - Symptom → cause: a masked value is rendered as its character length plus Java/Kotlin `String.hashCode()`. The hash has only 32 bits, is unsalted, and was designed for hash tables, not secret pseudonymization. Same-length collisions are trivial (`"Aa"` and `"BB"` have the same Java hash), while a log reader can cheaply hash a dictionary of candidate API keys, usernames, Basic credentials, or tenant tokens and compare the result. The KDoc calls the result “non-reversible” and `TwinContractTest` freezes one exact weak fingerprint as a cross-stack contract.
  - Triggering condition: a selected request or response header is configured under `masked`; exposure is most useful to an attacker when values have low entropy or a known candidate set.
  - Impact: supposedly protected values can be confirmed by offline guessing, distinct values can collapse to the same logged identity, and correlation/search conclusions based on the fingerprint can be wrong. Operators may select sensitive headers believing `masked` is a security boundary.
  - Fix strategy: define the privacy goal explicitly. For correlation without offline guessing, use a keyed HMAC with a host-managed secret and an adequately sized encoded prefix; if only accidental plaintext prevention is intended, use a modern digest with enough bits and document dictionary risk. Version the wire format and coordinate the twin/web-client contract rather than retaining `String.hashCode()` for compatibility.

## 6. Systemic patterns

1. **Cross-module or documented “contract” pins preserve semantically defective behavior at three boundaries.** `TraceparentTest` requires a W3C-invalid header to parse, `TwinContractTest` locks the 32-bit masking fingerprint, and the real error integration test requires the response body to be missing. These tests are honest about current implementation decisions, but they turn interoperability, privacy, and completeness defects into changes that fail the build. Findings 2-4 are the concrete instances; remediation needs an intentional contract migration, not only an implementation edit.
2. **High-risk tests use cooperative ordering/input at four remaining edges.** Deferred commit tests have no later action, truncation uses ASCII, request capture has no replay subscription, and header-name validation is tested only for blank values. The suite is large and deterministic, but these inputs stop immediately before the state/order/encoding boundary that can falsify its claims. Findings 1, 5-8 explain the resulting blind spots.

### 7.1 Why finding 4 stays a documented boundary

**The mechanics.** WebFlux assembles the request path as `HttpWebHandlerAdapter → ExceptionHandlingWebHandler → FilteringWebHandler → DispatcherHandler`. This module is a `WebFilter` and therefore runs *inside* `FilteringWebHandler`. It captures the response body by handing the chain a *mutated* exchange whose response is `CapturingResponseDecorator`; that mutated exchange exists only for the downstream part of the chain. When a handler error is not resolved inside the chain, it propagates up to `ExceptionHandlingWebHandler`, which invokes the `WebExceptionHandler`s (Boot's `ErrorWebExceptionHandler` among them) with the exchange *it* was given — the original one, whose response is the undecorated Netty response. The error body is written there. `ServerWebExchange.getResponse()` is not replaceable on an existing exchange, so a filter cannot retroactively put its tee under the outer handler's pen.

**What a WebFilter can observe of that rendering.** The status and the final headers — the filter's commit callback reads them from the shared delegate, and finding 1's remediation made sure it reads them *after* the rendering actions. What it cannot observe are the bytes of the body, and with them the size sample.

**The options that were weighed and why each was rejected.**

1. *Decorate at the `HttpHandler`/`WebHandler` level* (a `WebHttpHandlerBuilder` customizer or a `WebHandlerDecorator` registered ahead of `ExceptionHandlingWebHandler`). This is the only place that sees the outer error rendering. It is also a different integration point with a different contract: the module would stop being an ordered `WebFilter` that hosts can place, replace or back off (`EndpointLoggingFilter`, `@ConditionalOnMissingBean`), and it would have to duplicate the correlation/MDC wiring in a second component or move it wholesale — an architectural change to a module whose twin is a servlet filter with byte-identical configuration, not a defect fix.
2. *Register the module's own `WebExceptionHandler` ordered first and render through the decorated response.* This takes error rendering away from Boot (error attributes, `server.error.*` properties, `ProblemDetail` support, the host's own handlers) — a behavior change for every host, and a second copy of logic this module has no business owning.
3. *Re-wrap the original response in place.* Not available: `ServerWebExchange` offers `mutate()` (a new exchange) and nothing that swaps the response of an existing one; `AbstractServerHttpResponse` exposes no write hook other than `beforeCommit`, which sees headers, never body bytes.
4. *Read the body back from the Netty response.* Reactor Netty streams the bytes to the socket; there is no buffered copy to read once the outer handler has written.

**Why the residual is acceptable.** The information lost is the body of Boot's standard error rendering (the `{"timestamp","status","error","path"}` JSON or the HTML error page) and its size sample. The event already carries what an incident analysis needs from that response: the final status, the final headers, the outcome `failure`, and — as the event's cause — the exception itself, which is strictly more informative than the rendered body derived from it. The size metric's contract is narrowed explicitly rather than silently: it measures the bytes that flowed through the *application's* response path; globally rendered error bodies are outside it. Locally handled responses (controller advice, `ResponseStatusException` resolved in the dispatch, handlers that write their own error body) traverse the decorator normally and are fully captured.

**Why it is pinned rather than only documented.** `RequestLoggingWebFilterIntegrationTest` asserts on the real error path that the client receives a body *and* the event carries no `endpoint_response_body`. Anyone who moves capture to an integration point that can see the outer rendering (option 1, if a future need justifies it) has to flip that assertion consciously; until then the test keeps the boundary from drifting into an unnoticed half-capture.

**If the error body is needed after all.** The path is option 1 — an `HttpHandler`-level decoration registered ahead of `ExceptionHandlingWebHandler` — and it is an architecture change, not a follow-up fix: it moves capture (and with it the decision which response instance the tee sits on) out of the `WebFilter` contract that both endpoint-logging twins share. Per the repository's rule for changes of that size, it starts with a short decision document (options, the favoured one, the consequences for filter ordering, host back-off via `EndpointLoggingFilter`/`@ConditionalOnMissingBean`, and twin parity), not with code. Until that decision is taken, the pinned integration test is the contract.
