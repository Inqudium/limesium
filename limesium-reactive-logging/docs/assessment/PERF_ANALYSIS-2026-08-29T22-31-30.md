## 1. Executive summary

**No measurement artefacts were supplied; this is a hypothesis-generating static analysis** — every finding below is a prioritized measurement candidate, not a proven cost, and the report contains no P1 items because no unbounded-retention mechanism exists in the module. The module is a per-request WebFilter (two variants, Reactor and coroutine, sharing one `ExchangeLifecycle`), so essentially all of its cost is *request-scoped work multiplied by request rate*: wiring (correlation id, header snapshot, traceparent parse, `Exchange` allocation), an operator-chain assembly, and one guarded emission with MDC scope, string assembly and ~12 structured fields. The code is conspicuously performance-literate: patterns are parsed once at construction, level gates precede all message/field assembly, the body tee copies at most the configured cap and copies nothing in count-only mode, the `Mono` specialization of `writeWith` is preserved, and zero-copy trade-offs are documented. What remains are four measurable per-request hypotheses: (1) config-derived structures (lowercased exclude/mask sets in `HeaderLogProperties.select`) rebuilt on every call; (2) `mask()` doing a `MessageDigest.getInstance` lookup plus eight `String.format("%02x")` calls per masked header value; (3) body-size/read meters re-resolved through Micrometer's builder + registry lookup on every emission instead of a cached reference; (4) `UUID.randomUUID()`'s `SecureRandom` as a potential lock-contention point on event-loop threads when callers do not propagate the correlation header. Memory retention is clean: all state is request-scoped, meters are bounded by handler-template cardinality, and the one deliberate "stays open" case (never-committing error responses) parks on a gauge, not in a collection.

**Performance verdict:**
1. **Dominant cost:** allocation rate — small, transient, request-scoped objects (maps, pairs, strings, meter ids, boxed field values) created per exchange; CPU work is secondary (SHA-256 masking, UUID generation), retention is negligible by construction. This rests on counted allocations in source, not on measurement.
2. **Scaling risk:** the module scales linearly with request rate and adds no super-linear term; the first plausible break points at 10×–100× load are the two process-wide synchronization points it touches — `SecureRandom` inside `UUID.randomUUID()` (only for header-less traffic) and the single `AtomicLong` open-exchange gauge — plus per-resumption MDC reinstallation in the coroutine variant for suspension-heavy handlers.
3. **Highest leverage:** (a) cache the per-emission Micrometer meter lookups (finding 3) and (b) precompute the config-derived lowercase sets and the masking hex path (findings 1–2) — both are contained, semantics-free changes; but per the evidence rules, **measure first** (plan M1–M3, or the one wide-angle load test M5 that can retire all of them at once if the filter's total share proves negligible).

- [ ] 1. [`<pkg>/RequestLoggingProperties.kt:174` — `HeaderLogProperties.select`] {P2} {Mechanism: established} {Effect: estimated} {Cost type: allocation} {Lifetime: transient} Config-derived lowercase sets and per-name lowercasing rebuilt on every call
  - Mechanism: `excludes.map { it.lowercase() }.toSet()` and `masked.map { it.lowercase() }.toSet()` (lines 174–175) are recomputed from the immutable `HeaderLogProperties` on every invocation, plus `it.lowercase()` per candidate name in the filter and mask steps (lines 179, 182) and the intermediate collections of the `filter`/`mapNotNull`/`map` chain. The inputs never change after binding; everything derived here is per-instance constant.
  - Per execution: CPU `100 ns - 10 µs` (basis: string lowercasing + two set constructions over small lists); allocation `10 - 100 objects` (basis: counted — 2 sets, 2 backing maps, N lowercased strings, 3 intermediate lists, N pairs; for the assumed 2–5 entries roughly 15–40 objects).
  - Frequency: 2× per request (request side at wiring, response side at emission) — but ONLY when header logging is configured (`includes` non-empty); the shipped default short-circuits at line 171. Assumed rate: 1 000/s at 500 req/s (load-profile assumption "headers configured").
  - Aggregate: (10–100 objects × 1 000/s) → order of 10⁴–10⁵ transient objects/s from configuration data that could exist once. Effect on GC: unknown (young-gen only).
  - Scaling: linear in request rate and in the size of the include/exclude/mask lists; the `*` include adds `distinctBy { it.lowercase() }` over all message headers (line 177), scaling with header count.
  - Verification: JMH (plan M3); refutation: if `select()` measures < ~200 ns and < 500 B per call at realistic configs, the finding retires to P4.
  - Optimization sketch: precompute the lowercased exclude/mask sets (and `maskAll`) once in the `HeaderLogProperties` constructor/`init`; the per-call work then reduces to the name loop.
  - Change risk: low — private derivation from immutable state; no API or semantics change. (Shared pattern with the servlet twin — see systemic pattern S1.)

- [ ] 2. [`<pkg>/RequestLoggingProperties.kt:203` — `HeaderLogProperties.mask`] {P2} {Mechanism: established} {Effect: estimated} {Cost type: CPU} {Lifetime: transient} Per-value `MessageDigest.getInstance` plus eight `String.format`-based hex conversions
  - Mechanism: every masked header value performs a JCA provider lookup (`MessageDigest.getInstance("SHA-256")`, line 204), digests, then renders 8 bytes via `digest.take(8)` (boxes bytes into a `List<Byte>`) and `"%02x".format(it)` per byte (line 205) — each `format` call parses the format string and allocates a `Formatter` + `StringBuilder`, followed by `joinToString`.
  - Per execution: CPU `100 ns - 10 µs`, plausibly at the upper edge (basis: 8 independent `String.format` invocations plus provider lookup plus SHA-256 of a short input — each individually a known sub-µs operation, stacked ~10–20×); allocation `10 - 100 objects` (basis: counted — ~4 objects per format call × 8, digest instance + internal buffers, boxed list, ≈ 40–50).
  - Frequency: per masked header per request — assumed 1–2 masked headers → ~500–1 000/s under the assumed profile; zero with the shipped default (masking is opt-in).
  - Aggregate: order of 10⁴ format-call executions/s; total effect unknown without measurement.
  - Scaling: linear in request rate × masked-header count; independent of value length beyond the digest itself.
  - Verification: JMH (plan M2); refutation: < ~500 ns and < 1 KB per `mask()` call retires it.
  - Optimization sketch: render the 8 digest bytes through a nibble/hex lookup table (or `java.util.HexFormat`) instead of per-byte `String.format`; optionally reuse the digest via a thread-safe holder. No output change — the fingerprint format is a twin contract and stays byte-identical.
  - Change risk: low, but the output is contract-pinned across both twins — the identical change belongs in the servlet module too (pattern S1).

## 6. Systemic patterns

- **S1 — Config-derived work redone per call in the shared properties classes** (findings 1 and 2). `HeaderLogProperties.select`'s lowercase sets and `mask`'s digest/hex path recompute per call what the immutable configuration determines once. Occurrences: 2 call sites in this module (`ExchangeLifecycle.kt:312`, `ExchangeLogEmitter.kt:174`) — and the pattern is a TWIN CONTRACT: the same `HeaderLogProperties` design exists in `./limesium-servlet-logging` (counting basis: the module README/KDoc declare key-for-key parity; grep for `HeaderLogProperties` across both modules → 2 production definitions). Remediation in one twin without the other would fork the shared class design; treat as one cross-module change.
- **S2 — Meter resolution instead of meter reference on the per-emission path** (finding 3). Three sites (`requestBodyRead`, 2× `recordBodySize` targets) rebuild builder + id per call, while the fixed-tag meters at the top of the same class are exemplary pre-registered references (counting basis: read of `EndpointLoggingMetrics.kt` — 3 lazy sites vs 4 pre-registered families). One caching layer fixes all three.

Not a cost pattern, but systemic and worth naming: the fail-open try/catch fabric (every host-facing call guarded, `reportQuietly` inline) adds no measurable steady-state cost — exception handlers are free until thrown — and was NOT flagged anywhere.

## 8. Examined and unremarkable

Categories checked and found clean (with the deciding evidence):

- **Retention & leaks:** no unbounded collection anywhere. `reportedConflicts` is bounded by meter-name count (`EndpointLoggingMetrics.kt:38`); per-`uri` meters are bounded by handler-template cardinality with a single `UNKNOWN` fallback bucket (`EndpointLoggingMetrics.kt:260`) — no per-path cardinality explosion; `Exchange` objects are released at emission, and the documented never-commits case parks on a gauge (a number), not in a collection; no `ThreadLocal` owned by the module (MDC entries are scoped and restored, `Mdc.kt:78`); listeners/accessors are registered once, idempotently (`EndpointMdcContextPropagation.kt:52`).
- **Repeated construction of expensive objects:** include patterns parsed once at construction (`ExchangeLifecycle.kt:40`); traceparent regexes are compiled constants (`Traceparent.kt:20-23`); loggers are static/per-class. The two exceptions found became findings 2 and 3.
- **Logging discipline:** every message/field assembly sits behind a level gate (`ExchangeLogEmitter.kt:46, 156`) and metrics are recorded before the gate by documented design; no `toString()` of large graphs; bodies are cap-bounded and off by default.
- **Reactive rules:** no blocking calls on the event loop (SHA-256/UUID are CPU, not I/O — the UUID contention angle is finding 4); no `publishOn`/`subscribeOn` boundaries introduced; the `Mono` write specialization is deliberately preserved (`CapturingDecorators.kt:104-108`); no per-element `Mono`/`Flux` creation beyond one `map` per body publisher; no `flatMap` concurrency issues (none used); backpressure untouched (pure `map` tee).
- **Buffers & copies on the wire path:** the tee never re-wraps or retains `DataBuffer`s — ownership and release semantics are those of an undecorated exchange; the copy is bounded by `remainingCapacity()` and is zero in count-only mode (`CapturingDecorators.kt:23-38`). The emission-side copy chain is finding 6 (bounded, opt-in).
- **Exceptions as control flow:** none — all catch blocks are genuine fail-open containment, free until thrown; no stack-trace-suppression tricks needed.
- **Boxing:** checked; the residue (~a dozen boxed field values per emission) is finding 11 (P4, leave).
- **Time sources:** exactly two `nanoTime` reads per exchange (start at wiring, end at emission) — minimal; log timestamps are delegated to the backend by design (`NanoTimeSource.kt`).
- **Algorithmic complexity:** everything on the request path is O(headers + patterns + prefixes) with small constants; no nested loops over unbounded data, no repeated traversals.
- **Startup & footprint:** two auto-configurations, a handful of beans, pattern parsing at construction — negligible; no component scanning of its own.
- **Call-site polymorphism / JIT:** the per-request virtual calls (`NanoTimeSource`, `CorrelationIdGenerator`, `EndpointLoggingFilter`) are monomorphic in any real deployment (one implementation each per context) — inlining-friendly; no decorator stacks beyond the two body decorators.
- **Observability of the module itself:** present and thoughtful (fail-open counters, events counter, liveness gauge) — the absence finding this section normally carries does not apply.
