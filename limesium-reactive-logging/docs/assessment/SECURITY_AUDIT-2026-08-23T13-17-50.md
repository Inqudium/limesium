## 1. Executive summary

`limesium-reactive-logging` is a small, auto-configured WebFlux `WebFilter` library (no controllers, no persistence, no outbound calls, no deserialization, no SpEL, no reflection, no secrets) that logs one structured line per HTTP exchange and feeds six Micrometer meters. Its attack surface is therefore narrow: every request reaches the filter, but the only things the module does with request data are **log it**, **echo one header back**, and **match the path against configured patterns**. No finding in the Critical or High class was identified; the module contains none of the sink classes (SQL, command, file, SSRF, deserialization, expression evaluation) the audit prompt targets.

The one finding worth scheduling is a **log-injection vector (CWE-117, Medium)**: the logged request path and query string are taken from `java.net.URI.getPath()/getQuery()`, which percent-**decode** their input, so `%0A`/`%0D` in the request target become real line breaks inside the exchange message, the `endpoint_route` MDC value and the `endpoint_url_path`/`endpoint_url_query` fields. A structured (JSON) encoder neutralises this; a plain-text appender lets an unauthenticated client forge complete log lines. The servlet twin is **not** affected the same way because it logs the raw `requestURI`. Everything else is Low: opt-in verbatim header/body logging is a sensitive-data exposure surface that the module documents and leaves to the operator; the header-masking fingerprint is unsalted by design; trace and correlation ids are adopted from untrusted headers without further constraint; and the deliberate fail-open contract means the exchange log is an observability aid, not a security control.

Overall the code is defensively written - every host-facing call is guarded, memory use is bounded by configuration, the correlation header name is validated against the RFC 9110 token grammar at startup, `traceparent` parsing is strict, and `UUID.randomUUID()` (SecureRandom-backed) is used for generated ids. One remediation (finding 1) and a handful of hardening notes are the whole result.

## 2. Scope & methodology

- **Audited:** the 19 production files of the module, its Spring auto-configuration import, and its Maven descriptor. Every file was read completely; request-derived values were traced from their source (`ServerHttpRequest` headers, URI, body `DataBuffer`s, WebFlux attributes) to every sink (SLF4J event, MDC, Reactor context, response header, Micrometer tag).
- **Not audited:** tests; the host application's configuration (no `application.yml` exists in the module); the servlet twin beyond contract comparison; Netty/Reactor Netty internals (only their documented header-validation behaviour was relied upon - see finding 1 and the limitations).
- **Detected stack:** Spring Boot 4.1.0 auto-configuration; **WebFlux (reactive)** only - `@ConditionalOnWebApplication(type = REACTIVE)`; no Spring Security in scope (the module neither depends on nor interacts with it); no persistence; Kotlin 2.4.10 with `-Xjsr305=strict`; two filter variants (Reactor, coroutine) sharing one `ExchangeLifecycle`.
- **Local verification:** the code was not executed against a running server (per the audit rule, no live tests without a go-ahead). The decoding behaviour behind finding 1 was confirmed with a standalone JDK check of `java.net.URI` (`/api/th%0Aings?x=%0Ay` → path `/api/th<LF>ings`, query `x=<LF>y`). The module's own test suite was not used as evidence.
- **Limitations / blind spots:** (1) no SCA tool run - dependency CVE status is unverified; (2) Netty's header-value validation (which keeps CR/LF out of adopted header values) is assumed from Netty's documented default `validateHeaders=true`, not proven against the host's actual server configuration; (3) the security impact of the MDC/Reactor-context propagation depends on the host's encoder and on other libraries sharing the global `ContextRegistry`, which are outside the scope.

### 🟡 Medium

- [x] 1. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:288-289`] {Medium} {Confidence: high} {CWE-117 Improper Output Neutralization for Logs; OWASP A09:2021 Security Logging and Monitoring Failures} Percent-decoded request path and query string are logged unneutralised - `%0A`/`%0D` in the request target become line breaks in the exchange log.
  - Source → Sink: `request.uri.path` and `request.uri.query` (`java.net.URI.getPath()/getQuery()`, which **decode** percent-escapes - verified with a standalone JDK check) → `Exchange.path`/`Exchange.query` → (a) the message text `"Endpoint http exchange ${method} ${path} -> …"` in `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLogEmitter.kt:53` (arrival line) and `:192` (exchange line); (b) the MDC entry `endpoint_route` via `MdcScope` (`./…/Mdc.kt:49`) and the Reactor context (`./…/RequestLoggingWebFilter.kt:99`, propagated into handler MDC under automatic context propagation, and into `MDCContext` in `./…/CoRequestLoggingWebFilter.kt:126`); (c) the structured fields `endpoint_url_path`/`endpoint_url_query` (`./…/ExchangeLogEmitter.kt:55-57`, `:197-202`); (d) the internal WARN breadcrumb (`./…/ExchangeLifecycle.kt:182-189`) and the fail-open error messages, which also interpolate `exchange.path`.
  - Impact: an unauthenticated client can forge complete, correctly formatted log lines (including a fake `endpoint_request_id=` suffix and fake follow-up events) in every appender that renders the message or MDC as plain text, e.g. a `PatternLayout` console/file appender or a text-based Kafka pipeline. Because the value also travels into the handler-side MDC, **every application log line of that request** carries the injected text, not only the exchange line. Structured JSON encoders (Boot `StructuredLogEncoder`, `logstash-logback-encoder`, Logback `JsonEncoder`) escape control characters and are not affected - which is why this is Medium rather than High. The same property lets a client inject other terminal control sequences (ANSI escapes via `%1B`) into operator terminals.
  - Reachability: from outside, unauthenticated, on every request that reaches the filter (the filter runs at `HIGHEST_PRECEDENCE + 10`, before Spring Security would reject the request; a 404 is logged too). Note that the servlet twin logs `request.requestURI`, which is the raw (still-encoded) URI, and is therefore not affected the same way; the twins differ here.
  - Fix strategy: log the raw (encoded) path and query - WebFlux exposes them via `request.path.value()` / `uri.rawPath` / `uri.rawQuery` - or neutralise control characters (at least CR, LF, and C0/C1 controls) once when the `Exchange` is wired, so that every downstream sink (message, MDC, context, fields, breadcrumbs) sees a sanitised value. Pin the choice with a test in both twins so the path contract stays aligned.

### 🟢 Low

- [ ] 2. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:292-295`, `./…/ExchangeLogEmitter.kt:173-190`, `./…/RequestLoggingProperties.kt:176`] {Low} {Confidence: high} {CWE-532 Insertion of Sensitive Information into Log File; OWASP A09:2021} Opt-in verbatim logging of headers and bodies; the `*` include logs every header the message carries, credentials included, unless the operator excludes or masks them.
  - Source → Sink: all request headers (`request.headers[name]`) and response headers, request/response body bytes (`BoundedBodyCapture.loggedValue`) → `endpoint_request_headers`/`endpoint_response_headers`/`endpoint_request_body`/`endpoint_response_body` fields.
  - Impact: `Authorization`, `Cookie`, `Set-Cookie`, API keys, and personal data in bodies reach the log index in clear text when the operator enables these options without a matching `excludes`/`masked` list. Bodies are never masked (documented as out of scope). The exception `toString()` logged in the WARN breadcrumb (`./…/ExchangeLifecycle.kt:182-189`) can likewise carry data from exception messages.
  - Reachability: only when enabled by configuration (`log-*-body`, `*-headers.includes`); defaults log nothing. The behaviour is documented in the reference configuration and both guides as an operator decision, which is why this is recorded as Low rather than Medium.
  - Fix strategy: consider a built-in default `masked`/`excludes` set for well-known credential headers (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`) that applies when `*` is included, and state the body-logging data-protection caveat next to the property in the reference configuration.

- [ ] 3. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/RequestLoggingProperties.kt:202-206`] {Low} {Confidence: high} {CWE-328 Use of Weak Hash / CWE-916 Use of Password Hash With Insufficient Computational Effort; OWASP A02:2021 Cryptographic Failures} Header masking is an unsalted, unkeyed 64-bit SHA-256 prefix - it hides the plaintext but confirms guesses.
  - Source → Sink: masked header value → `"${length}:${sha256[0..8]}"` in the logged header field.
  - Impact: a reader of the log index with a candidate list (usernames, tenant ids, short API keys, bearer tokens of known format) can confirm a candidate by hashing it; the fingerprint also leaks the exact value length. For high-entropy secrets the scheme is adequate. The limitation is documented on the `mask` function and in both guides.
  - Reachability: only when `masked` is configured.
  - Fix strategy: keep the stable-correlation property but add an optional per-deployment key (HMAC) so that fingerprints are not confirmable offline; or recommend `excludes` over `masked` for low-entropy values (already documented).

- [ ] 4. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:284`, `./…/Traceparent.kt:31-52`, `./…/ExchangeLogEmitter.kt:165-171`] {Low} {Confidence: high} {CWE-345 Insufficient Verification of Data Authenticity; OWASP A09:2021} The trace id written to the `traceId` MDC key and the message suffix is taken verbatim from the client's `traceparent` header.

  - Reachability: from outside, every request with the header.
  - Fix strategy: when a Micrometer tracing bridge is present, prefer the trace id the bridge established for the server span (readable from the observation context or the bridge's MDC on the handler path) over the raw header; otherwise document that `traceId` reflects the caller's claim.

- [ ] 5. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:250-258`] {Low} {Confidence: medium} {CWE-20 Improper Input Validation; OWASP A09:2021} The adopted correlation id is unconstrained (any non-blank value up to the server's header-size limit) and is echoed back, logged inline, put into the MDC and the Reactor context.
  - Source → Sink: `X-Correlation-Id` request header (configurable name) → response header of the same name; `endpoint_request_id` MDC/context; message suffix `[endpoint_request_id=…]`; breadcrumbs.

Reflection of the value in the response header is harmless for browsers (no script context).
  - Reachability: from outside, every request.
  - Fix strategy: optionally validate adopted ids against a configurable length bound and character class (e.g. RFC 9110 token or a UUID/ULID shape) and fall back to a generated id when the check fails, counting the rejection on the existing `source=generated` tag or a new one.

- [x] 6. [`./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:62-77` and the 14 `reportQuietly` sites listed under pattern B] {Low} {Confidence: high} {CWE-778 Insufficient Logging (by design); OWASP A09:2021} Fail-open by contract: any failure in the module's own path silently removes the exchange from the log, so the exchange log cannot serve as an audit trail with completeness guarantees.
  - Source → Sink: not an injection - a design property. A failing host collaborator (MDC adapter, appender, `MeterRegistry`, response facade) degrades the filter to a pass-through or drops the event.

## 6. Systemic patterns

**Pattern A - untrusted request data is rendered verbatim into log records (6 sites; counted by reading `ExchangeLifecycle.wireExchange` and both emitter methods).** Path and query (finding 1), correlation id (finding 5), all headers and both bodies (finding 2), and `traceparent` ids (finding 4) are copied from the request into the event, the message, and the MDC without a single neutralisation point. Only `traceparent` and the configured header *name* are validated; values are trusted as text. Representative locations: `./limesium-reactive-logging/src/main/kotlin/eu/inqudium/limesium/reactive/logging/ExchangeLifecycle.kt:252`, `:284`, `:288-289`, `:292-295`; `./…/ExchangeLogEmitter.kt:173-190`. Because all six flow through `Exchange` (`./…/Exchange.kt`), a single sanitisation step at wiring time would cover every sink - the reason finding 1's fix strategy targets the `Exchange` construction rather than the emitter. Bodies deserve the same treatment only for the plain-text case (CR/LF inside `endpoint_request_body` is expected content for JSON encoders).

**Pattern B - fail-open swallowing of every host-facing call (14 `reportQuietly` sites, via `grep -c 'reportQuietly {'` over `*.kt` in scope; plus the `registerOrFallback` meter fallback).** Locations: `./…/CoRequestLoggingWebFilter.kt:113`; `./…/ExchangeLogEmitter.kt:64, 69, 93, 98, 134`; `./…/EndpointLoggingMetrics.kt:163`; `./…/ExchangeLifecycle.kt:66, 120, 125, 142, 147, 214, 222`. This is the module's deliberate contract (finding 6) and is implemented consistently - every site counts on the fail-open meter and reports on the module's own logger - so it is listed as a pattern for awareness, not as a defect. The security-relevant consequence is that the exchange log has no completeness guarantee; the counters are the compensating control.

**Checked and not found (for the record):** SQL/R2DBC queries, `Runtime.exec`/`ProcessBuilder`, file system access, outbound HTTP clients (SSRF), XML parsing (XXE), Java/Jackson/YAML deserialization, SpEL/script evaluation (`spring-expression` is on the compile classpath transitively via `spring-context` but is not referenced), JNDI lookups, reflection with untrusted names, Thymeleaf/FreeMarker templates, redirects, CORS configuration, JWT/crypto handling, hardcoded secrets (no configuration files in the module), Actuator exposure (none configured by the module - it only *consumes* the host's `MeterRegistry`), user-supplied regular expressions (all four `Traceparent` regexes and `HTTP_FIELD_NAME` are fixed-length or simple character classes - no ReDoS), insecure randomness (`UUID.randomUUID()` is SecureRandom-backed). Memory bounds: body capture is bounded by `max-body-bytes`, count-only mode copies nothing, header logging is bounded by the container's header limits, meter tag cardinality is bounded (handler template, closed vocabularies).

### Addendum (2026-08-23) - the servlet twin's finding 1, applied here

The servlet audit (`./limesium-servlet-logging/docs/assessment/SECURITY_AUDIT-2026-08-23T13-26-06.md`,
finding 1) asked whether activation matching sees the request target the way the router does. Checked
against this module at `1b67b8ec` with the same standalone `PathPattern` probe: the **exclude** side was
already correct (`shouldNotFilter` received the decoded `uri.path`, so `/%61ctuator/health` was excluded);
the **include** side decoded twice - the decoded `uri.path` was re-parsed into a `PathContainer` whose
segments decode again - and therefore accepted `/api%2Fthings` for `/api/**` although the WebFlux router
sees a single segment `api/things` and does not serve it, and collapsed `%252F` to `/`. No evasion
(the divergence only produced *extra* events), so no new finding is raised; it was **aligned for twin
parity**: both filter variants now hand the raw `ServerHttpRequest.path` (the `RequestPath` the router
matches) to `ExchangeLifecycle.shouldNotFilter`, which matches the includes against it and the exclude
prefixes against the decoded path rebuilt from its segments - the same code shape as the servlet twin.
Pinned by `RequestLoggingWebFilterTest` `should match activation on the raw request path exactly as the
WebFlux router does`. Property KDoc and guide (§4.4) updated accordingly.
