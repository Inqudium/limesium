## 1. Executive summary

The module is a mature, well-documented servlet logging library with explicit fail-open behavior, bounded body capture, exactly-once completion emission, injected time, and unusually broad unit and real-Tomcat integration coverage. No Critical production defect was found, and all remediations claimed by the existing assessment history were rechecked against the current code rather than carried forward unchecked. The most concrete production risk is a check-then-set race between servlet timeout and error callbacks that can overwrite the documented timeout precedence and misclassify a timed-out exchange as a generic failure. The async-dispatch exception path also calls the host logging backend before rethrowing the application exception, allowing a logging double fault to mask the original exception despite the fail-open contract. Two meter updates remain coupled to exchange wiring/emission, so a selectively broken host meter can suppress logging or report an already emitted event as dropped. Finally, an emission with no captured trace context leaves any pre-existing destruction-thread trace keys in place and can therefore attribute the event to an unrelated trace. The repeated weakness is narrow rather than architectural: three collaborator calls at fail-open boundaries are not independently isolated.

**Test verdict:** The suite is generally a reliable safety net: deterministic unit tests carry most behavior, while a focused real-Tomcat integration class validates MVC, async dispatch, error rendering, and body capture. Its main reliability defect is that the test advertised as proving timeout precedence invokes the callbacks only in a fixed sequence, so it remains green for the production race in finding 2. The pyramid is healthy rather than integration-heavy, but these score-4/5 edge paths remain materially under-proven:

- real concurrent `onTimeout`/`onError` interleavings with a shared start barrier;
- an async-dispatch application exception combined with a throwing logging backend;
- selectively failing correlation/event counters while logging otherwise remains healthy;
- emission without captured trace ids on a destruction thread that already carries trace MDC.

## 5. Findings

### 🔴 Critical

No Critical findings.

### 🟠 High

- [x] 1. [FILE:LINE — `./limesium-servlet-logging/src/test/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitterTest.kt:126`] {High} {Confidence: high} {test quality / concurrency} The test advertised as proving timeout precedence is a sham concurrency test and stays green for finding 2
  - Symptom → cause: The test states that `TIMED_OUT` must win regardless of evaluation order, but invokes `onTimeout` and `onError` sequentially on the test thread. It can never exercise the check-then-set interleaving that overwrites `TIMED_OUT` in production.
  - Triggering condition: The test gives false confidence whenever the production callbacks can overlap; no parallel start signal, contention, or repeated interleaving is used.
  - Impact: A score-4 async lifecycle invariant appears explicitly protected while the real race remains undetectable by the suite, increasing the chance of shipping incorrect timeout telemetry.
  - Fix strategy: Add a deterministic contention test with a shared start barrier and enough controlled repetitions to expose the forbidden terminal transition. Assert the state and emitted classification after both callback tasks finish, and propagate worker failures to the test thread.

### 🟡 Medium

- [x] 2. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/Exchange.kt:93`] {Medium} {Confidence: high} {correctness / concurrency} Concurrent timeout and error callbacks can overwrite the documented timeout precedence
  - Symptom → cause: `onError` performs a non-atomic read/check/write on the volatile `asyncDisposition`. If it reads `NONE`, `onTimeout` then writes `TIMED_OUT`, and `onError` finally writes `ERRORED`, the timeout terminal state is lost; volatile visibility does not make that compound transition atomic.
  - Triggering condition: Only when servlet timeout and error processing overlap on different threads in that interleaving. Servlet async callbacks are not confined to one application thread, and the inspected Tomcat lifecycle invokes listener callbacks outside a single lock that would serialize this compound operation.
  - Impact: A genuinely timed-out exchange can be emitted as `ERROR`/`failure` instead of `WARN`/`timeout`, corrupting alert and SLO telemetry and contradicting the class's stated absorbing timeout rule.
  - Fix strategy: Represent disposition changes as an atomic state transition in which `TIMED_OUT` is absorbing and `ERRORED` can replace only `NONE`. Keep cause selection consistent with the chosen terminal-state policy.

- [x] 3. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:291`] {Medium} {Confidence: high} {robustness / error handling} A failing async-dispatch breadcrumb can mask the original application exception
  - Symptom → cause: After recording the async handler exception, the catch block calls `internalLog.warn` directly before `throw e`. If the host logging backend throws from its level check, TurboFilter, or appender, that second exception escapes instead, unlike the guarded initial-dispatch breadcrumb path.
  - Triggering condition: Edge-case double fault: an async MVC dispatch fails while the module logger's backend also throws. The suite already treats throwing Logback infrastructure as an in-scope host failure, but covers it only on other logging paths.
  - Impact: Container error handling receives the logging failure rather than the application failure, changing diagnostics and potentially the rendered error while violating the method's documented fail-open behavior.
  - Fix strategy: Keep failure capture and rethrow independent from breadcrumb emission. Run the breadcrumb as an isolated best-effort diagnostic and always preserve the original application exception as the primary throwable.

- [x] 4. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:359`] {Medium} {Confidence: medium} {robustness / observability} Operational counter increments are not isolated from the exchange lifecycle they measure
  - Symptom → cause: A throwing correlation-source counter aborts `wireExchange`, so the request passes through with no exchange event; conversely, the unguarded `metrics.eventEmitted(outcome)` at `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:230` runs after `.log()` and can make the outer handler count/report an emission failure even though the event already exists. Body-size meters are explicitly isolated, but these counters are not.
  - Triggering condition: Only with a host `MeterRegistry`/`Counter` implementation that registers successfully and later throws selectively on increment, or equivalent runtime registry failure. The test suite already injects throwing counters as a supported fail-open fault model, but not these healthy-logging/selective-counter combinations.
  - Impact: One broken metric can suppress otherwise viable exchange logging, and the fail-open/event counters can cease to be truthful reconciliation signals about whether a line was emitted.
  - Fix strategy: Isolate every meter update from wiring and log emission, and distinguish a metric-update failure from a log-emission failure. Preserve the successfully emitted event as success even if its accounting counter cannot be incremented.

- [x] 5. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/Mdc.kt:49`] {Medium} {Confidence: high} {correctness / context propagation} Missing captured trace values do not suppress unrelated trace MDC on the destruction thread
  - Symptom → cause: `MdcScope` owns and restores only keys whose new value is non-null. During completion emission, a null captured `traceId` or `spanId` therefore leaves any pre-existing value on the destruction thread untouched, and the logging event snapshots that foreign value even though the inline trace suffix correctly remains absent or partial.
  - Triggering condition: Edge case where the exchange captured no trace id, or only one id, while the thread executing `requestDestroyed` carries a stale or independently owned `traceId`/`spanId` from another scope.
  - Impact: The exchange event can be joined to the wrong trace, or to an internally inconsistent trace/span pair, undermining incident reconstruction while the current empty-MDC tests remain green.
  - Fix strategy: Give the emission scope explicit ownership of both trace keys for its lifetime: absent captured values must be temporarily removed and all previous values restored afterward. Preserve the current additive behavior for the separate chain scope, where the host bridge remains authoritative.

## 6. Systemic patterns

### Fail-open boundaries do not isolate every collaborator side effect

Approximately **3 occurrences**, counted by manual review of production logger and meter calls at the module's declared fail-open boundaries: the unguarded async breadcrumb at `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:291`, the correlation counter at `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:359`, and the post-log event counter at `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:230`. Findings 3 and 4 are distinct manifestations: one can replace an application exception, while the other can suppress or falsely account for an exchange event. The surrounding implementation already applies best-effort guards to most comparable calls, so remediation should audit boundary ownership consistently rather than patch only the three representatives.

## 7. Remediation status (2026-08-22)

All five findings were re-verified against the code before remediation and confirmed. The module suite is green after the changes (`mvn -pl limesium-servlet-logging verify`: 137 tests, ktlint clean).

| Finding | Resolution |
|---|---|
| 1 — timeout-precedence test is sequential only | **Fixed.** `ExchangeLogEmitterTest` adds a contention test: 500 exchanges, each with `onTimeout` and `onError` released from a shared `CountDownLatch` onto two worker threads, worker failures propagated through `Future.get`, every exchange asserted `TIMED_OUT` and the last one emitted as `timeout`. No sleeps; with the CAS of finding 2 the invariant holds deterministically. The sequential test stays as the order-rule pin. |
| 2 — check-then-set overwrites `TIMED_OUT` | **Fixed.** `Exchange.asyncDisposition` is backed by an `AtomicReference`; `markTimedOut()` sets unconditionally (absorbing), `markErrored()` is `compareAndSet(NONE, ERRORED)`. `AsyncOutcomeMarker` calls these; the cause selection (`asyncFailure`) is unchanged. |
| 3 — async breadcrumb can mask the application exception | **Fixed.** The `filterAsyncDispatch` catch block wraps the breadcrumb `warn` in its own guard: a throwing backend is counted `stage=wiring` (reported through `reportQuietly`) and the ORIGINAL exception is rethrown. Pinned in `RequestLoggingFilterAsyncTest` with a `TurboFilter` that throws for the module logger: the container receives the handler's exception, the event carries it, `wiring=1`. |
| 4 — operational counters not isolated | **Fixed** (twin parity with finding 3 of the reactive module's CODE_ANALYSIS-2026-08-22T23-32-09.md). `EndpointLoggingMetrics.correlationId` and `eventEmitted` run through `updateQuietly`: a throwing host counter is counted `stage=wiring` and warned, the exchange is wired and logged regardless, and a successful `.log()` is never reported as an emission failure. `RequestLoggingFailOpenCounterTest` pins both with a registry that throws selectively on one meter (event emitted, `emission=0`, `wiring=1`). |
| 5 — uncaptured trace ids leave foreign MDC values on the event | **Fixed.** `MdcScope` gains `ownsTraceKeys`: the emitter opens its scope with it, so an uncaptured `traceId`/`spanId` is REMOVED for the emission and restored afterwards; the chain scope (bridge authoritative) keeps the additive behavior. `RequestLoggingFilterTraceContextTest` pins the stale-pair and the stale-half cases, including restoration of the thread's values. |
