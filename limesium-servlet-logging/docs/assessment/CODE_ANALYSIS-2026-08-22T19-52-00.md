## 1. Executive summary

The module is compact, deliberately fail-open, and unusually well covered for servlet lifecycle, response wrapping, metrics, and real-Tomcat integration. No Critical or High defect was identified, and the reviewed code contains no persistence, messaging, reactive chain, blocking remote call, explicit scheduler, or shared lock whose failure could corrupt business data. The main remaining weakness is the MVC asynchronous redispatch: the filter deliberately skips it, which leaves framework-managed result rendering without the endpoint MDC and prevents exceptions from asynchronous controller results from reaching the exchange failure classification. The second material correctness issue is request-body text rendering: the logging charset is frozen when the wrapper is constructed, although the Servlet contract permits downstream code to set the encoding before the body is read. Invalid but non-blank correlation-header names are another operational blind spot because configuration succeeds and every request then degrades into the per-request fail-open path instead of failing at startup. Body truncation is memory-safe, but an arbitrary byte boundary can split a multi-byte character and corrupt the displayed prefix. The implementation is deterministic and resource-bounded under its documented single-writer servlet model; all six findings affect observability correctness or test confidence rather than the client-visible request/response result.

**Test verdict.** The suite is a credible safety net overall: fast deterministic unit tests carry most behavior, while two bounded real-Tomcat test classes prove container and tracing conventions. It is not inverted or visibly flaky, but its strongest async and body tests stop immediately before the remaining defect-bearing boundaries and therefore create localized false confidence.

- The real async test proves the Callable worker and final event, but not the framework-managed ASYNC redispatch or a Callable/DeferredResult failure.
- The body tests prove fixed UTF-8 and ASCII truncation, but not a downstream encoding change or a multi-byte character crossing the capture boundary.
- No fresh build or reproducing test was run because the governing prompt requires explicit go-ahead before local execution; findings were verified by code flow and local framework source contracts.

### 🟡 Medium

- [x] 1. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:71`] {Medium} {Confidence: high} {correctness / concurrency} The MVC ASYNC redispatch is skipped, losing endpoint MDC on that framework-managed thread and hiding asynchronous controller failures from the exchange classification
  - Symptom → cause: `OncePerRequestFilter.shouldNotFilterAsyncDispatch()` remains `true`, so the T3 ASYNC dispatch runs the downstream MVC result/error handling without an `MdcScope` and without the filter's exception capture. Spring supplies a thrown `Callable` exception as `concurrentResult` to `EndpointMdcCallableInterceptor.postProcess`, but `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/EndpointMdcCallableInterceptor.kt:53` ignores it. The final event therefore commonly falls back to `status >= 500`: WARN/failure without the application cause, whereas the equivalent synchronous unhandled exception is ERROR/failure with the cause. Logs emitted by response advice, interceptors, converters, or exception rendering on the redispatch thread also lack `endpoint_*` MDC.
  - Triggering condition: a Spring MVC `Callable`/`WebAsyncTask` (and analogous DeferredResult flow) whose result is rendered or whose application work fails after the initial dispatch; deterministic for logs on the redispatch thread, and deterministic for the missing failure cause when no container-level `AsyncListener.onError` occurs.
  - Impact: incorrect severity and missing cause in the module's core exchange record, plus broken correlation for application/framework logs on one phase of every MVC async exchange; alerting and incident diagnosis can disagree between synchronous and asynchronous endpoints.
  - Fix strategy: participate in ASYNC dispatches using the already-attached `Exchange` without rewiring/restarting it, opening only a scoped MDC and recording propagated failures. Also capture `Throwable` concurrent results for Callable and DeferredResult processing so application failures survive to final classification.

- [x] 2. [FILE:LINE — `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/CapturingRequestWrapper.kt:46`] {Medium} {Confidence: high} {correctness} The request-body logging charset is frozen before downstream code is still legally allowed to change it
  - Symptom → cause: `bodyCharset` is resolved eagerly in the wrapper constructor, before the chain runs, while `readerCharset()` correctly consults `characterEncoding` only when the application asks for the reader. The Servlet 6.1 contract permits `setCharacterEncoding` until parameters or the reader are consumed; a downstream filter/controller can therefore read the intended text while `ExchangeLogEmitter` later decodes the captured bytes with the stale constructor-time charset at `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:195`.
  - Triggering condition: body logging enabled; the request encoding is absent or different at filter entry; downstream code sets a valid encoding before calling `getReader`; the body contains bytes whose decoding differs between the two charsets.
  - Impact: the request proceeds correctly, but `endpoint_request_body` contains replacement characters or different text, undermining the forensic value of the logging feature on a fully valid Servlet flow.
  - Fix strategy: bind the log-rendering charset when the body API is first selected/read, after downstream encoding configuration has taken effect, and retain that effective charset with the capture for destruction-time rendering.

## 7. Remediation status (2026-08-22)

All 6 findings were re-verified against the code before remediation and confirmed; finding 1 additionally against Spring Framework 7.0.8's `OncePerRequestFilter` source (the already-filtered attribute is removed after the initial pass, so with `shouldNotFilterAsyncDispatch() == false` the ASYNC dispatch invokes `doFilterInternal` again). The module suite is green (`mvn -pl limesium-servlet-logging verify`: 130 tests, ktlint clean).

| Finding | Resolution |
|---|---|
| 1 — ASYNC redispatch skipped | **Fixed.** `RequestLoggingFilter.shouldNotFilterAsyncDispatch()` returns `false`; `doFilterInternal` routes an ASYNC dispatch to `filterAsyncDispatch`, which reuses the `Exchange` attached by the initial pass (no re-wiring, no second correlation id or gauge increment), opens the chain-wide `MdcScope` around the dispatch and records an exception propagating out of it as `exchange.failure` with the usual breadcrumb — exactly the sync contract. A failing `Callable`/`DeferredResult` therefore classifies ERROR/failure with its cause; rendering-phase logs carry the `endpoint_*` identity. The `concurrentResult` throwable is deliberately NOT captured in `postProcess`: a handled async exception (`@ExceptionHandler` in the dispatch) never propagates and is classified by status, as on the sync path. A request without an attached exchange passes through. |
| 2 — log charset frozen at construction | **Fixed.** `CapturingRequestWrapper.bodyCharset` is bound in `teeOverDelegate()` — the first stream/reader selection, the moment the servlet contract freezes the encoding — and resolved at query time for a body that was never read. |
| 3 — invalid correlation header name passes binding | **Fixed** (lockstep, `f58ca1dc`). `RequestLoggingProperties` validates `correlationIdHeader` against the RFC 9110 `token` grammar at construction; `RequestLoggingPropertiesTest` covers whitespace, separators, non-ASCII and the full `tchar` set. |
| 4 — async tests stop at the worker thread | **Fixed.** `RequestLoggingFilterAsyncTest` drives the `OncePerRequestFilter` entry for an initial dispatch that starts async and an ASYNC dispatch whose chain observes the MDC and throws (one ERROR event with cause, original correlation id, clean thread MDC), plus the no-exchange pass-through. `RequestLoggingFilterIntegrationTest` adds real-Tomcat cases: a `ResponseBodyAdvice` proves the MDC during result rendering of `/it/async`, `/it/async-boom` (throwing `Callable`) and `/it/deferred-boom` (`DeferredResult.setErrorResult`) both answer 500 and log ERROR/failure with the cause and `endpoint_async=true`. |
| 5 — body tests avoid the mutable-encoding boundary | **Fixed.** `RequestLoggingFilterBodyAndHeaderTest` declares ISO-8859-1 at entry, switches to UTF-8 inside the chain before reading a UTF-8 body, and asserts both the application-visible text and `endpoint_request_body` (`hällo`, not `hÃ¤llo`). |
