## 1. Executive summary

Style-wise the module is mature and consistent: ktlint runs in the build and is green, so formatting is a non-topic; visibility is deliberately narrowed (`internal` on every collaborator, `private` companions where nothing leaks), injection is constructor-based throughout, configuration is one `@ConfigurationProperties` data class with `require`-based invariants, stateless contracts are `fun interface`s with companion defaults, and stateless holders are `object`s. "Java in Kotlin" traces are rare — there is no `!!` outside one justified site, no `lateinit` in production code, no util class, no manual `IllegalArgumentException` where `require` fits, and the few `var`s are either cross-thread state on `Exchange` or accessor caches in the servlet wrappers. Naming follows the domain (`Exchange`, `BoundedBodyCapture`, `AsyncOutcomeMarker`), test names are full backtick sentences, assertions are AssertJ only, no mocking library appears, time and ids are injected everywhere.

Two clusters stand out. First, the **documentation cross-reference style**: 26 KDoc/comment passages justify a design by pointing at "assessment finding N, 2026-08-22 analysis" — a reference that was unambiguous when one analysis existed and is now ambiguous, since three analyses of the same date (and one of the day before) live in `docs/assessment/`; a reader following the pointer lands on the wrong document half the time. Second, the **test-convention gaps**: CLAUDE.md prescribes Given/When/Then markers "without exception", yet six test methods carry none and 25 carry only a partial set — mostly in the contract-pin tests, where a reviewer may well judge the markers as noise, but the convention does not grant that exception. The remaining findings are small Kotlin-idiom points (Java-style definite assignment before a `when` in the emitter, a `var` builder reassignment chain, one `!!`), one file whose name hides its main class, an `Enumeration` converted two different ways in one method, and inline fully-qualified names in two test classes. No enforced rule is violated; nothing is actively misleading.

### 🟠 High

- [x] 1. [`./limesium-servlet-logging/src/test/kotlin/eu/inqudium/limesium/servlet/logging/TwinContractTest.kt:13` (representative; 6 methods without any marker, 25 with a partial set)] {High} {Confidence: high} {Test style} Test methods without the mandated Given/When/Then markers
  - Actual pattern: six `@Test` methods carry no `// Given` / `// When` / `// Then` comment at all — all four in `TwinContractTest`, the single test in `HandlerMappingAttributeTest`, and `should be the literal strings the component template maps` in `EndpointLogFieldTest` (counting basis: `awk` over every `@Test` body, looking for the three markers including the combined `// Given/When` and `// When/Then` forms). A further 25 methods carry one or two of the three (e.g. `// Then` only, or `// When/Then` without a Given) — mostly single-assertion pins and the Spring integration tests, where the "Given" is the class-level context.
  - Reference: `./CLAUDE.md`, "Testing conventions": "Given / When / Then structure, with comments marking each block" — "Any new test Claude writes must follow this format **without exception**."
  - Idiomatic alternative: add the markers even where a block is trivial (a one-line `// Given/When/Then: ...` is an accepted house form, used e.g. in `TraceparentTest` of the twin); for the integration classes, a `// Given: the auto-configured application` line before the first call makes the class-level context explicit per method.
  - Effect: consistency with a non-negotiable project convention; the pin tests are exactly the ones a future maintainer skims fastest, so the missing structure costs more there than in a long test.

### 🟡 Medium

- [x] 2. [`./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:160`] {Medium} {Confidence: high} {Kotlin idiom} Java-style definite assignment before a `when` statement instead of `when` as an expression
  - Actual pattern: `var level: Level`, `val outcome: String`, `val cause: Throwable?` are declared unassigned, then each of five `when` branches assigns all three; afterwards `level` is mutated once more for the slow escalation (`if (slow && level == Level.INFO) level = Level.WARN`). The same shape exists in the reactive twin's emitter.
  - Reference: Kotlin Coding Conventions ("Prefer using the expression form of `try`, `if`, and `when`"; "prefer `val` over `var`") and the module's own dominant pattern — every other multi-branch decision in the module (`traceSuffix`, `readerCharset`, `charsetOrDefault`, the properties' `select`) is an expression.
  - Idiomatic alternative: let the `when` produce one value — a small private data holder or a triple of `(level, outcome, cause)` — bind it with `val`, and derive the final level as a second `val` from the base level and the slow flag. Strategy only, no code here.
  - Effect: readability (the classification becomes one readable table), immutability (no `var level`), and the compiler's exhaustiveness check replaces the definite-assignment check.

- [x] 3. [`./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:27` (representative; 26 occurrences across `src/main`)] {Medium} {Confidence: high} {Docs} Design rationale anchored to analysis documents by a now-ambiguous reference
  - Actual pattern: KDoc and comments justify decisions with "(assessment finding 2, 2026-08-22 analysis)", "(assessment finding 4)", "(architecture review finding 5, 2026-08-22T18-12-19)" and similar — 26 such references in production code (counting basis: `grep -o "assessment finding …|architecture review finding …|finding N, 2026-08-22 …"`). Thirteen use the date-only form "2026-08-22 analysis", four name the `T16-35-46` report, six the `T16-49-01` report, three the `T18-12-19` review; a few carry no date at all ("assessment finding 4"). `./limesium-servlet-logging/docs/assessment/` now holds three documents dated 2026-08-22 and one dated 2026-08-21, each with its own finding numbering.
  - Reference: the house pattern itself — the KDoc style of this module is *why*-oriented and explicitly traceable, which is its strength; a reference that no longer identifies its target defeats that purpose. Strategy only.
  - Effect: maintainability of the rationale trail; consistency (three reference formats coexist in one module).
