## 1. Executive summary

**No measurement artefacts were supplied; this is a hypothesis-generating static analysis** — a prioritized measurement list, not an optimization plan, and it contains no P1 because the module has no unbounded-retention mechanism. The module is a per-request `OncePerRequestFilter` plus an emission at request destruction; its cost is request-scoped work × request rate, exactly like its reactive twin, and it shares the twin's two systemic hypotheses: config-derived structures rebuilt per call (`HeaderLogProperties.select`'s lowercase sets, `mask()`'s digest-plus-`String.format` hex path) and body meters re-resolved through Micrometer's builder + registry lookup on every emission. Three findings are servlet-specific. First — and the only one that runs with the SHIPPED DEFAULTS — `shouldNotFilter` parses the request URI into a `PathContainer` on every dispatch even when no include patterns and no exclude prefixes are configured, so the parse result is discarded unused; the reactive twin gets its path container for free from the request. Second, the response wrapper's Writer path encodes every written character a second time through its capture encoder — including past the capture cap and in count-only (measure-only) mode — so template-rendered responses pay a full second encoding of their body whenever a response capture exists. Third, per request the filter eagerly materializes the header-name list and registers a fresh async-MDC interceptor even in applications that never go async. `UUID.randomUUID()`'s process-global `SecureRandom` is, as in the twin, the plausible contention point for header-less traffic — amplified here by the ~200-thread worker pool. Memory retention is clean: exchange state rides a request attribute removed at destruction, the interceptor's ThreadLocal is removed in a `finally`, meters are bounded by handler-template cardinality, and the servlet `BoundedBodyCapture` is even cheaper than the reactive one (no lock — a volatile-piggyback single-writer model).

**Performance verdict:**
1. **Dominant cost:** allocation rate — small transient request-scoped objects (path containers, maps, lists, meter ids, boxed field values); CPU second (masking, UUID, and — where the Writer path is hit with capture on — double body encoding); retention negligible by construction. Based on counted source allocations, not measurement.
2. **Scaling risk:** linear in request rate, no super-linear term. First plausible break points at 10×–100×: `SecureRandom` serialization across ~200 worker threads for header-less traffic, and — data-volume-dependent, not rate-dependent — the Writer-path double encoding, which grows with response size while everything else is size-independent.
3. **Highest leverage:** (a) gate the `PathContainer.parsePath` behind non-empty include/exclude configuration — it is the only default-path finding and the fix is one condition; (b) cache the per-emission meter lookups and precompute the config-derived structures (shared with the twin — one cross-module change each). Per the evidence rules: measure first (plan M0/M1–M3); the one wide-angle load test M0 can retire most of the list at once if the filter's total share proves negligible.

### 🟠 P2 — measure first, then decide

- [ ] 1. [`<pkg>/RequestLoggingFilter.kt:117` — `shouldNotFilter`] {P2} {Mechanism: established} {Effect: estimated} {Cost type: allocation} {Lifetime: transient} `PathContainer.parsePath` on every dispatch, even with no include/exclude configuration
  - Mechanism: `PathContainer.parsePath(request.requestURI)` runs unconditionally at line 117, BEFORE the two early returns that make it unnecessary — with `includePathPatterns` and `excludePathPrefixes` both empty (the SHIPPED DEFAULT), the parsed container is discarded unused. The parse tokenizes the URI into separator/segment elements (one object per element plus the list and container). Because `shouldNotFilterAsyncDispatch()` is `false`, async exchanges pay it twice (REQUEST + ASYNC dispatch). The reactive twin has no equivalent cost — WebFlux hands it the already-parsed `RequestPath`.
  - Per execution: CPU `100 ns - 10 µs` (basis: known cost of segment tokenization over a typical 3–6-segment URI); allocation `10 - 100 objects` (basis: counted — ~2 objects per path element + container + list; ~10–30 for typical paths).
  - Frequency: per dispatch, UNCONDITIONALLY — the only finding in this report that is active with the shipped defaults. 500+/s assumed.
  - Aggregate: order of 10⁴ transient objects/s at the assumed rate, for nothing when no patterns are configured. Effect on latency/GC: unknown.
  - Scaling: linear in request rate × path segment count.
  - Verification: JMH (plan M2a) or the M0 alloc flame graph (`PathContainer.parsePath` under `shouldNotFilter`); refutation: < ~150 ns / < 300 B per call.
  - Optimization sketch: return `false` immediately when both lists are empty, before parsing; the container is then built only for configurations that use it.
  - Change risk: minimal — pure short-circuit, semantics for configured patterns unchanged.

- [ ] 2. [`<pkg>/RequestLoggingProperties.kt:159` — `HeaderLogProperties.select`] {P2} {Mechanism: established} {Effect: estimated} {Cost type: allocation} {Lifetime: transient} Config-derived lowercase sets rebuilt on every call — systemic pattern S1, identical to the reactive twin's finding 1

  - Per execution: CPU `100 ns - 10 µs`; allocation `10 - 100 objects` (basis: counted, ~15–40 for 2–5 entries). Frequency: 2× per request when header logging is configured (assumed → 1 000/s); zero with defaults.
  - Aggregate: 10⁴–10⁵ transient objects/s. Scaling: linear in rate × list sizes; the `*` include adds `distinctBy` over all header names.
  - Verification: JMH (plan M3, shared with the twin); refutation threshold as there.
  - Optimization sketch: precompute the lowercase sets and `maskAll` in `init` — one change, both twins.
  - Change risk: low; twin-contract class, change both modules together.

- [ ] 5. [`<pkg>/CapturingResponseWrapper.kt:176-202` — the Writer-path capture encoder] {P2} {Mechanism: established} {Effect: estimated} {Cost type: CPU} {Lifetime: transient} Every character written through `getWriter` is encoded a SECOND time — past the capture cap and in count-only mode
  - Mechanism: the tee writer forwards each chunk to the real writer and then to `captureEncoder` (an `OutputStreamWriter` over the capture) followed by `flush()` (lines 196–202). The encoder encodes ALL characters to bytes so the capture can count them — also once `buffer.size() >= maxBytes` (bytes are then only counted, but the char→byte encoding still runs), and in COUNT-ONLY mode (`maxBytes = 0`, i.e. `measure-response-body-size` without `log-response-body`), where the entire response body is encoded solely to obtain its byte count. The container encodes the same characters again for the wire — a full duplicate encoding of the body, linear in body SIZE, not in the cap. Reachability: only responses written through `getWriter` (template engines, JSPs, manual writer use); Spring MVC's JSON/String converters write through the OutputStream, whose tee is O(cap) copy + O(1) count.
  - Per execution: CPU `unknown` per request (linear in body chars — for a 100 KB HTML page a second full UTF-8 encode; basis for the mechanism: the code path; no basis for a per-request class, hence unknown); allocation `< 10 objects` per writer creation (encoder + adapters), no per-chunk allocation.
  - Frequency: per Writer-rendered response when a response capture exists (log OR measure); assumed profile: measuring on → every template response.
  - Aggregate: unknown; grows with response volume, not request count.
  - Scaling: linear in response size — the one finding here that 100× PAYLOAD makes worse while everything else is size-independent.
  - Verification: JMH or targeted load test (plan M4): Thymeleaf-style writer output of 10/100/1000 KB with `measure-response-body-size` on vs off; signal: throughput delta and `StreamEncoder` frames. Refutation: < ~2 % cost at 100 KB.
  - Optimization sketch: once the cap is exhausted (and always in count-only mode), replace exact encoding with a byte-count estimate or a cheaper counting encoder — BUT this trades metric exactness for CPU; the honest alternative is documenting that response-size measuring on writer-based endpoints costs a second encode. Decide after M4.
  - Change risk: moderate — the exact byte count is the metric's contract, and the stateful-encoder correctness (surrogate pairs, finding-pinned) must not regress.

- [ ] 6. [`<pkg>/CorrelationIdGenerator.kt:17` — `RANDOM_UUID`] {P2} {Mechanism: established} {Effect: unknown} {Cost type: wait (+ CPU)} {Lifetime: transient} `UUID.randomUUID()`'s shared `SecureRandom` under a ~200-thread worker pool — twin finding 4, amplified by thread count

## 8. Examined and unremarkable

- **Retention & leaks:** none. The exchange rides a request attribute REMOVED at destruction (`RequestLoggingFilter.kt:459` — also the double-decrement guard for the gauge); the interceptor's `ThreadLocal` is removed in `postProcess`'s `finally` (`EndpointMdcCallableInterceptor.kt:62`) and the ThreadLocal itself is per-request and unreachable after it; `reportedConflicts` bounded by meter names; per-`uri` meters bounded by template cardinality with the `UNKNOWN` fallback; `MdcScope` restores every touched key, with partial-install rollback. No caches, no queues, no listeners that outlive their request.
- **Repeated construction of expensive objects:** include patterns parsed once at construction (`RequestLoggingFilter.kt:100`); the RFC-9110 regex is validated at binding, not per request; loggers static. The exceptions found are findings 3 and 4.
- **Logging discipline:** level gates before all assembly (`ExchangeLogEmitter.kt:48, 183`); metrics before the gate by documented design; breadcrumbs only on failure paths; bodies cap-bounded and off by default; no `toString()` of object graphs.
- **Algorithmic complexity:** O(headers + patterns + prefixes) per request, small constants; no nested loops over unbounded data; no repeated traversals.
- **Concurrency:** the servlet `BoundedBodyCapture` is LOCK-FREE (single-writer model with a volatile piggyback publish — cheaper than the reactive twin's `ReentrantLock`, and the handoff reasoning is documented in the class); `AsyncDisposition` is one atomic with built-in precedence — no lock, no spin; no locks held across I/O anywhere in the module.
- **Exceptions as control flow:** none — all catch blocks are genuine containment, free until thrown; the either-or `check()`s in the request wrapper throw only on application contract violations.
- **Boxing:** checked; residue is finding 12 (P4).
- **Time sources:** exactly two `nanoTime` reads per exchange; wall-clock timestamps delegated to the backend.
- **Data copying on the wire path:** both tees forward to the real stream FIRST and copy second; nothing is withheld or replayed (no `copyBodyToResponse` equivalent); the byte-stream tee copies at most the remaining cap and otherwise only counts. The writer-path second encoding is finding 5; the emission-time copy chain is finding 11.
- **Call-site polymorphism / JIT:** `NanoTimeSource`/`CorrelationIdGenerator` are monomorphic per deployment; the tee stream/writer are one anonymous class each per request — call sites in application code see the same shape throughout a request; no deep decorator stacks.
- **Startup & footprint:** one filter bean, one registration, one listener, patterns parsed once — negligible.
- **Virtual threads:** not assumed; if enabled by the host, the module's ThreadLocal use is request-scoped with guaranteed removal, and no `synchronized` is held across blocking calls — no pinning or multiplication mechanism found.
- **Observability of the module itself:** present (same meter family as the twin) — the usual absence finding does not apply.
