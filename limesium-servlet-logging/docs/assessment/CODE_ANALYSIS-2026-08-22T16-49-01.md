## 1. Executive summary

The module is compact, deliberately fail-open, and unusually explicit about its Servlet and logging contracts. Its primary synchronous and Spring MVC `Callable` paths have bounded capture, injected monotonic time and correlation generation, volatile/atomic async hand-offs, scoped MDC restoration, and substantial real-container coverage. No Critical or High defect was found. The most consequential defect is that `CapturingResponseWrapper.reset()` clears captured bytes but retains the now-stale cached writer/output stream, even though Servlet 6.1 explicitly resets the accessor-selection state; valid post-reset code can therefore receive a stale writer or mix access modes when body capture is enabled. The response correlation header is installed only before the chain and is not an invariant: downstream `setHeader` or `reset` calls can replace/remove the promised echo while the event and MDC retain the original identifier. Two configuration edges also produce misleading telemetry: the 32-bit masking fingerprint collides at realistic fixed-length-token cardinalities, and a positive sub-millisecond slow threshold rounds to zero milliseconds and classifies every request as slow. The production findings affect observability and edge-path response behavior, not persistence or business data, and are therefore Medium rather than High. One documentation statement about custom-filter registration contradicts the actual auto-configuration and its own test.

**Test verdict.** The 100-test suite is a strong safety net for the exercised paths: time and ids are injected, assertions are generally exact, no mocking library or sleep-based synchronization is used, and 11 real-Tomcat tests cap a broad non-network base of 89 tests (including six lightweight context-runner tests). The pyramid is healthy, but its highest-weight contract tests stop short of several adversarial boundary cases, and both real-HTTP test classes use blocking clients without request deadlines.

- `resetBuffer()` is proven, but the distinct `reset()` accessor-state contract is not.
- Correlation echo tests never let downstream code replace or reset the header.
- Masking and slow-threshold tests use friendly examples only; collisions and sub-millisecond values remain untested.
- A stalled embedded endpoint can block a real-HTTP test without a test-owned timeout.

### 🟡 Medium

- [x] 1. [./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/CapturingResponseWrapper.kt:57] {Medium} {Confidence: high} {correctness} `reset()` leaves cached response accessors stale and breaks the Servlet writer/stream state machine
  - Symptom → cause: Servlet 6.1 specifies that `reset()` clears whether `getWriter()` or `getOutputStream()` was selected and makes the previously returned object stale. The wrapper delegates `reset()` and clears only the capture, while retaining `teeWriter` and `teeStream`; a valid second accessor call can therefore return the stale object, retain the old charset, or later bypass the delegate's mutual-exclusion check through a cached opposite accessor.
  - Triggering condition: response body logging or measurement is enabled, an uncommitted response obtains a writer or stream, downstream code calls `reset()`, and then obtains an accessor again or switches access mode; exception handlers and response-rewriting filters are typical paths.
  - Impact: client-visible output may be encoded through stale state, valid Servlet code can behave differently only when logging is enabled, and the captured body/size can diverge from the final response.
  - Fix strategy: make full reset invalidate and finalize the wrapper's accessor/encoder state in lockstep with the delegate, while keeping `resetBuffer()`'s narrower semantics. Prove same-accessor reacquisition, writer-to-stream switching, stream-to-writer switching, and post-reset charset changes against a real Servlet implementation.

- [x] 2. [./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:269] {Medium} {Confidence: high} {correctness} The promised correlation-id echo can be overwritten or cleared downstream
  - Symptom → cause: the filter calls `setHeader` once before the chain, but neither protects nor reapplies that header. A controller/filter can replace it with another value, and `HttpServletResponse.reset()` clears it, while the exchange event and MDC continue to carry the original id.
  - Triggering condition: downstream code sets the configured correlation header, or resets an uncommitted response before returning; no exceptional container behavior is required.
  - Impact: the client receives no id or a different id from the logs, defeating support-case correlation on rewritten/error responses and contradicting the public “always echoed” contract.
  - Fix strategy: either enforce one authoritative value throughout response mutation/commit, including reset and async paths, or narrow the public contract explicitly. Add a real-container proof for downstream replacement and reset, not only a no-op chain and Tomcat's default error dispatch.

- [x] 3. [./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingProperties.kt:161] {Medium} {Confidence: high} {correctness} The 32-bit masking fingerprint creates false correlations at realistic cardinality
  - Symptom → cause: the fingerprint is only value length plus Java's 32-bit `String.hashCode()`. Fixed-length token populations therefore inherit a 32-bit birthday bound; distinct values can and do render identically, despite the test's broad “different values as different ones” claim.
  - Triggering condition: masked headers carry many distinct values of the same length, or any known equal-length hash collision occurs; this is a load/cardinality condition, not necessarily hostile input.
  - Impact: operators can join unrelated requests under one apparent masked token and draw wrong incident or traffic conclusions. This finding is about observability correctness; cryptographic secrecy is outside this analysis.
  - Fix strategy: use a substantially wider deterministic fingerprint with an explicitly documented collision model and change both endpoint-logging twins together. Test known collision inputs and a high-cardinality invariant rather than two friendly examples.

- [x] 4. [./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/ExchangeLogEmitter.kt:121] {Medium} {Confidence: high} {robustness} A valid positive sub-millisecond slow threshold rounds to zero and flags every request as slow
  - Symptom → cause: configuration validation accepts every positive `Duration`, but classification converts the threshold with `toMillis()`. Any threshold between zero and one millisecond becomes `0`, and the non-negative millisecond duration consequently satisfies the slow comparison for every exchange.
  - Triggering condition: `slowRequestThreshold` is configured programmatically or bound to a positive sub-millisecond duration.
  - Impact: all successful traffic escalates to WARN with `endpoint_slow=true`, producing false alerts and potentially a large avoidable log-volume increase.
  - Fix strategy: compare in a precision that preserves the configured threshold or reject values below the module's millisecond resolution during configuration binding. Pin just-below, exactly-at, and just-above boundary behavior.

- [x] 5. [./limesium-servlet-logging/src/test/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilterBodyAndHeaderTest.kt:300] {Medium} {Confidence: high} {test quality} High-weight contract tests prove friendly examples but omit four defect-bearing boundaries
  - Symptom → cause: the “Response reset handling” group invokes only `resetBuffer()`, the correlation tests use chains that do not mutate the correlation header, the masking test generalizes from one non-colliding unequal pair, and the slow-threshold test uses only whole milliseconds. All remain green with findings 1-4 present.
  - Triggering condition: a maintainer relies on these tests as proof of the broader reset, always-echoed, different-value, or positive-duration contracts.
  - Impact: the suite creates bounded false confidence around four score-5/score-3 production edges; mutations at the unexercised branches survive despite nearby green contract tests.
  - Fix strategy: extend the existing focused suites with mutation-sensitive adversarial cases for the exact four mechanisms, keeping injected time and no-mock isolation. Assertions should compare final client behavior, capture/metric state, and emitted identity rather than merely the presence of an event.

- [x] 6. [./limesium-servlet-logging/src/test/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilterIntegrationTest.kt:66] {Medium} {Confidence: high} {test quality} Real-HTTP integration calls have no request-owned deadline
  - Symptom → cause: both real-container classes use `HttpClient.newHttpClient()` and blocking `send()` calls without a connect or request timeout; the Maven Surefire configuration also defines no per-test/fork timeout. The appender's five-second bound starts only after the HTTP response has returned and cannot release a stalled `send()`.
  - Triggering condition: an embedded-server regression accepts a connection but never completes a response, or the local HTTP stack stalls.
  - Impact: CI can hang instead of producing a bounded failing test, consuming an executor indefinitely and obscuring the underlying regression.
  - Fix strategy: give every integration request a short explicit deadline and, where supported by the target JDK, close or deliberately share the client lifecycle. Preserve the event-driven appender wait as a separate bound for post-response emission.

## 7. Remediation status (2026-08-22)

All 7 findings were re-verified against the code before remediation and confirmed; finding 1 was additionally checked against the Servlet 6.1 `reset()` Javadoc ("It is legal, for instance, to call getWriter, reset and then getOutputStream"). The fixes landed in commit `1cd6b5a2` with the full module suite green (`mvn -pl limesium-servlet-logging verify`, 106 tests, ktlint clean). Findings 2 and 3 were resolved by narrowing and documenting the contract rather than by changing behavior; the rationale is given per row.

| Finding | Resolution |
|---|---|
| 1 — `reset()` leaves cached accessors stale | **Fixed.** `CapturingResponseWrapper.reset()` now drops the cached tee writer/stream together with the capture, in lockstep with the delegate's accessor-state reset; `resetBuffer()` keeps its narrower semantics. Pinned by two tests: writer → reset → charset change → writer (fresh instance, client and log bytes in the post-reset charset) and writer → reset → stream → reset → writer (the spec-permitted mode switch, no `IllegalStateException`). |
| 2 — correlation echo can be overwritten or cleared downstream | **Contract narrowed, documented.** Enforcing one authoritative value would require wrapping every response (the wrapper only exists when a body is captured) and would override an application that deliberately sets the header itself. The reference configuration now states the actual contract: the header is set once at filter entry and not re-asserted, so downstream `setHeader`/`reset` decides what the client sees while the event and the MDC keep the id resolved at entry. |
| 3 — 32-bit masking fingerprint collides at realistic cardinality | **Documented as a contract boundary.** The fingerprint is a literal cross-module contract (web-client `ExchangeDiaryLogging`, both endpoint-logging twins, pinned by `TwinContractTest`); widening it in one place would break the cross-module join the masking exists for. The `mask` KDoc now states the collision model (32 bits plus length, 2^-32 per-pair false-join chance, a correlation hint and not an identity), and a test pins the known collision `"Aa"`/`"BB"` so a future widening is a deliberate contract change across all three. |
| 4 — sub-millisecond slow threshold flags everything as slow | **Fixed.** `RequestLoggingProperties` rejects any threshold below one millisecond with a message naming the floor (the comparison stays at the logged millisecond resolution, so the resolution is made explicit instead of hidden). Pinned for `999_999 ns` (rejected), zero/negative (rejected) and `1 ms` (accepted) in the new `RequestLoggingPropertiesTest`. The reactive twin carries the same validation gap; it is the subject of its own analysis report. |
| 5 — example-only boundary proofs | **Fixed** for the three mechanisms that changed behavior or got a documented model (findings 1, 3, 4 — tests listed above). The correlation boundary (finding 2) is now a documented non-guarantee; a test asserting that the filter does *not* re-assert the header would pin an absence rather than a contract and was deliberately not added. |
| 6 — real-HTTP tests without a request deadline | **Fixed.** Both real-container classes build their `HttpClient` with a connect timeout and give every request a 15 s deadline; the appender's wait remains the separate bound for post-response emission. |
| 7 — README override contradicts the registration contract | **Fixed.** The README now says a custom `RequestLoggingFilter` bean replaces the filter while the auto-configured registration and the request-destruction listener stay wired around it, and points to `endpoint-logging.enabled=false` for removing the registration entirely. |
