## 1. Executive summary

`limesium-servlet-logging` is a small, auto-configured servlet filter library (`OncePerRequestFilter` plus a `ServletRequestListener`) with no controllers, no persistence, no outbound calls, no deserialization, no expression evaluation, no reflection on untrusted names, and no secrets. Every request reaches the filter, but the module does only three things with request data: **log it**, **echo one header back**, and **match the request URI against configured patterns**. No Critical or High finding was identified; none of the sink classes the audit prompt targets exists in the module.

The one finding worth scheduling is a **logging-coverage evasion (CWE-180, Medium)** that only applies when `include-path-patterns` is configured: the activation check matches the **raw, un-decoded, un-normalized** `request.requestURI`, while Tomcat and Spring MVC route on the **decoded and normalized** path. A client can therefore reach a handler under `/api/**` with a request target the include pattern does not recognise (`/%61pi/things`, `/./api/things`, `//api/things`) and have that exchange handled but **not logged**. With the default configuration (empty includes = log everything) the divergence is harmless. Notably, the raw-URI choice is also what protects this module from the log-injection finding of the reactive twin: percent-encoded control characters stay encoded in the logged path and query here, so the twins differ in opposite directions on the same design point.

Everything else is Low and mirrors the reactive audit: opt-in verbatim header/body logging is a sensitive-data surface the module documents and leaves to the operator; the masking fingerprint is unsalted by design; the adopted correlation id is unconstrained; bodies can carry line breaks into plain-text appenders; and the deliberate fail-open contract means the exchange log is an observability aid, not an audit trail. The code is defensively written: every host-facing call is guarded, memory is bounded by configuration, the correlation header name is validated against the RFC 9110 token grammar at startup, generated ids use `UUID.randomUUID()` (SecureRandom-backed), the request wrapper preserves the servlet decoding contract for the application, and the emission scope owns the trace keys so a stale id on a pooled thread cannot be attached to a foreign exchange.

### 🟡 Medium

- [x] 1. [`./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:110-118`] {Medium} {Confidence: medium} {CWE-180 Incorrect Behavior Order: Validate Before Canonicalize; OWASP A09:2021 Security Logging and Monitoring Failures} The include/exclude activation matches the raw request target, while the container and Spring MVC route on the decoded, normalized path - a handled request can evade `include-path-patterns`.
  - Source → Sink: `request.requestURI` (the request target as sent: still percent-encoded, dot-segments and duplicate slashes intact) → `shouldNotFilter`: `PathContainer.parsePath(path)` matched against the parsed `include-path-patterns`, then `excludePathPrefixes.any { path.startsWith(it) }`. Tomcat's `CoyoteAdapter` decodes and normalizes a *copy* of the URI for servlet mapping (collapsing `/./`, `/../`, `//`, decoding `%xx` except for the rejected encoded slash), and Spring MVC matches its `PathPattern`s against the decoded `RequestPath` - so `/%61pi/things`, `/./api/things` and `//api/things` all reach the handler mapped at `/api/things`, but none of them matches the include pattern `/api/**` against the raw string, and `shouldNotFilter` returns `true`.
  - Impact: with `include-path-patterns` configured, an unauthenticated client can have any included endpoint handle its request **without an exchange event, without the correlation echo and without the chain MDC** - the request is invisible to the exchange log, dashboards and the `events` counter, while nothing on the fail-open meter moves (the filter simply did not run). The exclude side diverges in the harmless direction (an obfuscated `/actuator/health` is logged rather than skipped). The reactive twin uses the decoded `uri.path` and WebFlux does not normalize dot-segments, so it is not affected in the same way - the two twins' documented "byte-identical activation semantics" hold only for plain, already-canonical targets.
  - Reachability: from outside, unauthenticated, but **only when `include-path-patterns` is non-empty** (default: empty, every endpoint logged). Requires a container that normalizes for mapping (Tomcat, Jetty and Undertow all do) - not verified live.
  - Fix strategy: match the activation against the same representation the container mapped on - the servlet-relative decoded path as Spring exposes it (`ServletRequestPathUtils`/`UrlPathHelper` with the MVC settings, or `RequestPath` from the request attribute Spring MVC sets) rather than the raw `requestURI` - and keep `endpoint_url_path` raw for the log. Pin the divergence with an integration test against embedded Tomcat in this module and align the twin's documentation on what "identical activation semantics" covers.

## 6. Systemic patterns

**Pattern A - untrusted request data is rendered verbatim into log records (5 sites; counted by reading `RequestLoggingFilter.wireExchange` and both emitter methods).** Raw path and query (safe against control characters here, see finding 5), correlation id (finding 4), all headers and both bodies (findings 2 and 5) are copied from the request into the event, the message and the MDC without a single neutralisation point; the bridge's trace ids are adopted from the MDC (trusted collaborator - whether the bridge honours an incoming `traceparent` is the bridge's policy, not this module's). Only the configured header *name* is validated. Representative locations: `./limesium-servlet-logging/src/main/kotlin/eu/inqudium/limesium/servlet/logging/RequestLoggingFilter.kt:374`, `:407-408`, `:411-412`, `:423-424`; `./…/ExchangeLogEmitter.kt:191-208`. All flow through `Exchange` (`./…/Exchange.kt`), so a single sanitisation step at wiring time would cover every sink for the plain-text case.

**Pattern B - fail-open swallowing of every host-facing call (16 `reportQuietly` sites, via `grep -c 'reportQuietly {'` over `*.kt` in scope; plus the `registerOrFallback` meter fallback).** Locations: `./…/RequestLoggingFilter.kt:140, 169, 220, 238, 273, 304, 321, 351`; `./…/ExchangeLogEmitter.kt:64, 69, 105, 110, 138`; `./…/EndpointLoggingMetrics.kt:168`; `./…/EndpointMdcCallableInterceptor.kt:42, 57`. This is the module's deliberate contract (finding 6) and is implemented consistently - every site counts on the fail-open meter and reports on the module's own logger - so it is listed for awareness, not as a defect.

**Checked and not found (for the record):** SQL/JPA/JDBC queries, `Runtime.exec`/`ProcessBuilder`, file system access, outbound HTTP clients (SSRF), XML parsing (XXE), Java/Jackson/YAML deserialization, SpEL/script evaluation (`spring-expression` is on the compile classpath transitively via `spring-context` but is not referenced), JNDI lookups, reflection with untrusted names, templates, redirects (the response wrapper only passes `sendRedirect` through and clears the capture), CORS/CSRF/session configuration (none - no Spring Security interaction), JWT/crypto handling beyond the documented fingerprint, hardcoded secrets (no configuration files in the module), Actuator exposure (none configured - the module only *consumes* the host's `MeterRegistry`), user-supplied regular expressions (`HTTP_FIELD_NAME` is a simple character class applied once at binding - no ReDoS; `PathPattern`s are operator-configured and parsed once), insecure randomness (`UUID.randomUUID()` is SecureRandom-backed), HTTP response splitting via the correlation echo (container-validated), request smuggling-relevant header handling (the module only reads, never rewrites, framing headers), log injection via path/query (raw URI - not a vector here, in contrast to the reactive twin), charset handling (`Charset.forName` on the client's declared encoding is caught in both call paths and the application's reader keeps the servlet contract). Memory bounds: body capture bounded by `max-body-bytes`, count-only mode buffers nothing, header logging bounded by the container's header limits, meter tag cardinality bounded (handler template, closed vocabularies). Thread hygiene: every `MdcScope` restores previous values on pooled threads, the async worker interceptor pairs install/restore on the same thread via a `ThreadLocal` it removes in `finally`.

| Finding | Resolution |
|---|---|
| 1 - activation on the raw request target diverges from routing (CWE-180) | **Partly refuted, residual fixed.** The audit assumed a byte-wise comparison on both sides. The *include* side never was one: `PathContainer.parsePath(requestURI)` produces segments whose `valueToMatch()` is **decoded**, and `PathPattern.matches` compares those - the same parser and the same matching Spring MVC's handler mapping uses on the same raw `requestURI`. `/%61pi/things` therefore matched `/api/**` already, and `/./api/things` and `//api/things` fail the include *and* Spring MVC's own `PathPattern` mapping alike (404 - Tomcat's normalized copy is used for servlet mapping only, the `DispatcherServlet` builds its `RequestPath` from the raw URI). The **Medium rating and the "handled but unlogged" impact do not hold**; the audit's "medium" confidence was warranted and the finding should be read together with this section. What remained true is the *exclude* side: `excludePathPrefixes.any { requestURI.startsWith(it) }` was byte-wise on the raw URI, so `/%61ctuator/health` escaped an `/actuator/health` exclude (harmless for probe noise, a leak when an operator excludes a sensitive route to keep its query strings out of the log). **Fixed:** `shouldNotFilter` parses the container once, matches the includes against it as before, and compares the exclude prefixes against the decoded path rebuilt from the container's segments (path parameters dropped, as in routing). Pinned in `RequestLoggingFilterTest` by `should exclude a percent-encoded variant of an excluded prefix` and, for the include side, `should include a percent-encoded variant of an included pattern and log the raw path` (which also pins that the logged path stays raw - the twin contract the reactive module adopted in its own audit's remediation). The property KDoc, the reference configuration and the guide (§4.4) now say "decoded path" instead of "plain prefix match". Residual, unchanged: with the legacy `AntPathMatcher` strategy Spring MVC decodes the full path and collapses `//`, which the include side does not - an operator choosing that strategy should use plain patterns. |
| 2 - opt-in verbatim headers/bodies (CWE-532) | **Not fixed - documented trade-off.** A built-in default `masked`/`excludes` set would change the observable semantics of `includes: ["*"]` in both twins and the reference configuration; credential logging is an operator decision with the caveats stated next to the properties. |
| 3 - unsalted fingerprint (CWE-328) | **Not fixed - documented trade-off.** A keyed (HMAC) fingerprint needs a new cross-twin configuration key and breaks the documented cross-module correlation with `web-client`'s diary, which uses the same unkeyed scheme. |
| 4 - unconstrained correlation id (CWE-20) | **Not fixed - needs a contract decision.** A length bound or shape check with generated fallback changes the correlation contract for every caller of both twins; CR/LF cannot arrive through this path (container framing), so the residual risk is collision/bloat, not injection. To be decided together with the reactive twin's finding 5. |
| 5 - line breaks in logged bodies and obs-text in headers (CWE-117, opt-in) | **Not fixed - documented.** Neutralising control characters in `loggedValue` would alter the logged body for structured encoders that handle them correctly, and the feature is opt-in; the plain-text caveat is stated in the guide's body-tee section. Revisit together with the reactive twin if a plain-text pipeline is a supported target. |
| 6 - fail-open is not an audit trail (CWE-778) | **Fixed (documentation).** The guide's fail-open section (§2.8) carries a security note stating that the exchange log is an observability feature with no completeness guarantee, that a regulatory audit trail must come from a fail-closed component, and which meters are the compensating controls. |
